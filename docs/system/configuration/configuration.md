# Конфигурация и состояние устройства

Для разбора транзакции нужны адрес ведомого, допустимые регистры
и правило записи. Эти сведения сервис получает из профиля устройства.
Файл профиля, рабочая конфигурация сервиса и физическое состояние
устройства изменяются разными операциями.

Место профиля в системе и состав связанных файлов показаны
в [общем описании конфигурации](../../configuration/configuration.md).
Здесь рассмотрим, как настройки участвуют в обработке транзакции.

## Загрузка профиля

При запуске приложение читает профили и передаёт их общему кодеку.
После проверки код запуска создаёт сервисы, связывает их с драйверами
и устанавливает рабочие параметры. Затем сервис использует свою
конфигурацию в памяти. Редактирование JSON на носителе автоматически
её не меняет.

Поддержка формата и проверка содержимого сосредоточены в общем коде.
Выбор файлов и операции с носителем выполняются средствами целевой ОС.
Порядок поиска, ошибки загрузки и различия ОС разобраны в
[загрузке, применении и сохранении](../../configuration/lifecycle.md).

## Участие политики в транзакции

Рассмотрим устройство I²C по адресу `0x2A` и запись `0x3B` в регистр
`0x10`. Это тот же учебный запрос, который далее проходит через
[ядро, драйвер и сервис I²C](../pl-subsystem/i2c/i2c.md).

Пользователь меняет правило и применяет конфигурацию. Следующая
транзакция проверяется уже по новой политике. Сервис сопоставляет
пару `0x10 = 0x3B` с правилами и только при разрешении вызывает
master-драйвер. Результат обмена обновляет состояние сервиса
и попадает в наблюдения.

Сохранение конфигурации определяет правила после следующего запуска.
Если оно завершается ошибкой, уже применённая политика остаётся
действующей в RAM. Физическая запись регистра остаётся отдельной
операцией сервиса. Изменение рабочей политики и запись её в файл
показаны в
[схеме применения и сохранения](../../configuration/lifecycle.md#Рабочие%20и%20сохранённые%20настройки).

## Начальные значения и кэш

`cache_seed` задаёт значения, которые программа может поместить в кэш
при загрузке. Они помечаются источником `settings`. Такой источник
показывает, что значение пришло из профиля. Присутствие устройства
и физическое значение регистра устанавливаются при обмене.

Затем кэш обновляют реальные операции. Для разных шин порядок публикации
различается: I²C может потребовать ответ на промах в ограниченное время,
MDIO отвечает из заранее подготовленной копии. Общая связь кэша с BRAM
описана в [механизме подсистем](../pl-subsystem/pl-subsystem.md),
а внешнее чтение его состояния — в [наблюдении](../observation/observation.md).

Карта регистров и форма используют снимки этого кэша для отображения.
Они не меняют правила сервиса и не запускают обмен на шине.
Связь полей регистра с показателями объясняется
в [описании карты](../../configuration/register-map.md).

Далее проследим запрос через [подсистемы PL](../pl-subsystem/pl-subsystem.md).
