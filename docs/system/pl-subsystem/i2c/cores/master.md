# Ведущее ядро I²C

В [исходном сценарии](../i2c.md) ведомому сервису понадобился байт
регистра `0x10`, которого нет в достоверном кэше. Теперь проследим,
как этот байт получает `I2C_master_0` на стороне физического устройства.

Сервис выбирает устройство и операцию. Драйвер готовит команду,
запускает ядро и ждёт результат. Аппаратура формирует такты, адрес,
данные и подтверждения. Полученное значение возвращается сервису,
а затем может стать ответом внешнему ведущему.

## Состав ядра

Работа master начинается с команды PS. Для передачи команды и для
возврата результата внутри ядра предусмотрены разные пути.

![Путь команды, автомат шины и приёмные модули master](../../../figures/architecture/pl-subsystem/i2c/cores/master/structure.svg)

*Рисунок 1. I²C master: состав ядра.*

PS обращается к `regs` через порт `s_axi`. Командные заголовки
и данные записи помещаются в TX FIFO — очередь слов. `tx_data_ctrl`
извлекает их по порядку и выдаёт engine отдельные пакеты адреса
и байтов. Признаки `tx_valid` и `tx_ready` согласуют передачу между
модулями.

`i2c_master_engine` выполняет обмен на SDA и SCL. При чтении байты
поступают через `rx_data_ctrl` в RX FIFO. Затем `rx_fifo_mux`
упаковывает их в слова и записывает результат в BRAM через `m_axi`.
FIFO позволяет приёмной ветви сохранять данные независимо от текущего
состояния автомата шины, пока в очереди есть место.

Эти части соединены в `top_i2c_master` и `i2c_master_wrapper`.
Аппаратная линия IRQ подключена к GIC, но текущий драйвер master
ожидает результат опросом CSR и IRQ через платформу L1.

## Подготовка команды

Для чтения регистра нужно выполнить несколько связанных действий
без вмешательства другой команды: передать указатель, поменять
направление и принять байт. Поэтому драйвер владеет ядром на протяжении
всего вызова.

![Подготовка операции сервисом и загрузка команды драйвером](../../../figures/architecture/pl-subsystem/i2c/cores/master/commands.svg)

*Рисунок 2. I²C master: подготовка команды.*

`bvstk_i2c_master_hw_transfer` удерживает mutex, ждёт свободного ядра
и очищает прежние признаки IRQ. Затем он записывает заголовки
и данные в TX FIFO и передаёт `CSR.start`. Блокировка не даёт двум
вызывающим сторонам перемешать команды. Очистка признаков не позволяет
принять старый результат за завершение нового чтения.

Заголовок задаёт одну фазу: адрес, направление, число байтов и способ
завершения. После заголовка записи идут слова передаваемых данных.
Для чтения достаточно заголовка с нужным количеством байтов.

| Операция | Содержимое TX FIFO |
|---|---|
| Запись | Заголовок W, затем слова данных |
| Чтение | Заголовок R с числом принимаемых байтов |
| Запись с последующим чтением | Заголовок W с признаком restart, данные записи, заголовок R |

`tx_data_ctrl` превращает эту последовательность в пакеты для engine.
Последний пакет фазы содержит `stop` или `restart`. Engine получает
инструкцию, как завершить фазу, вместе с её последним байтом.
Битовые поля заголовка приведены в справочном разделе ниже.

## Повторный START

Для регистра `0x10` устройства `0x2A` драйвер подготавливает две фазы.
Первая записывает указатель, вторая принимает один байт. Ядро получает
их за один запуск.

![Две фазы обмена из одной очереди команд](../../../figures/architecture/pl-subsystem/i2c/cores/master/repeated-start.svg)

*Рисунок 3. I²C master: две фазы из одной очереди.*

В TX FIFO сначала помещается заголовок записи длиной один байт
с `restart = 1`, затем байт `0x10`, затем заголовок чтения длиной
один байт с `restart = 0`.

Engine передаёт адрес с направлением W и указатель. Признак restart
на последнем пакете вызывает повторный START без промежуточного STOP.
Контроллер разбирает следующий заголовок и передаёт новый адресный
пакет с направлением R. Ядро принимает D0, выдаёт NACK и STOP.

На внешней стороне [slave](slave.md#запись-указателя-и-повторный-start)
в это время может ждать ответ от PS. Два повторных START принадлежат
двум разным обменам. Один сформировал внешний ведущий, второй — ядро
master по команде программы. Их связывает выбранный регистр и
возвращаемое значение.

Следующие рисунки отдельно показывают передачу и приём байтов,
из которых состоит такой обмен.

## Выполнение записи

Для изменения регистра сервис передаёт два байта: `0x10` как указатель
и `0x7B` как значение. При этом до запуска драйвера уже должна быть
проверена политика записи.

![Передача адреса и двух байтов с подтверждениями ведомого](../../../figures/architecture/pl-subsystem/i2c/cores/master/write.svg)

*Рисунок 4. I²C master: передача записи.*

После START ядро выдаёт адресный байт `0x54`, соответствующий `0x2A`
с направлением W. Оно отпускает SDA на девятом такте и проверяет ACK.
Затем из слова данных извлекаются `0x10` и `0x7B` в таком порядке.
Каждый байт также заканчивается проверкой ACK.

После последнего подтверждения признак `stop` завершает обмен.
Engine выдерживает условие STOP и возвращается в `IDLE`. Для этой
операции не требуется возвращать полезные данные в BRAM: драйверу
нужно дождаться свободного ядра и проверить отсутствие `ERR_ACK`.

Ядро одинаково передаёт указатель и значение как два байта. Значение
первого байта как номера регистра определяют сервис и ведомое устройство.
Для фазы выбора указателя перед чтением используется тот же механизм
передачи, но с одним байтом и завершением через restart.

## Выполнение чтения

После адреса с направлением R направление данных меняется. Такты
по-прежнему формирует master, а SDA с данными теперь задаёт устройство.

![Получение двух байтов и передача пакетов в приёмную ветвь](../../../figures/architecture/pl-subsystem/i2c/cores/master/read.svg)

*Рисунок 5. I²C master: приём байтов.*

На рисунке принимаются два байта, чтобы показать промежуточный ACK
и завершающий NACK. Engine передаёт адресный байт `0x55` и получает
подтверждение устройства. Затем собирает восемь бит D0 и выдаёт ACK.
После D1 последняя команда содержит `stop`, поэтому master выдаёт
NACK и завершает обмен. В исходном однобайтовом чтении NACK следует
сразу после D0.

Каждый принятый байт передаётся в `rx_data_ctrl`. Дальше он движется
к BRAM независимо от завершения STOP на шине. В какой-то момент
engine уже может быть свободен, а запись результата в память ещё
не закончена. Поэтому одного состояния `IDLE` для успешного чтения
недостаточно.

Драйвер ждёт одновременно свободное ядро, новый `DATA_VALID`
и отсутствие `ERR_ACK`. Только затем он извлекает нужное число
байтов из BRAM. Ведущий сервис обновляет кэш и возвращает значение
вызывающему коду — в нашем примере ведомому сервису.

## Приёмные буферы и BRAM

Проследим промежуток между получением байта на шине и появлением
`DATA_VALID`. Здесь происходит преобразование внутренних пакетов
в представление, которое читает программа.

![Приём пакетов, запись результата и передача готовности в PS](../../../figures/architecture/pl-subsystem/i2c/cores/master/buffers.svg)

*Рисунок 6. I²C master: приём и публикация результата.*

RX FIFO хранит по одному `packet_view_t` в 32-битном слове.
Кроме байта, в пакете есть адрес и признаки фазы. `rx_fifo_mux`
извлекает поле `data` и собирает по четыре полезных байта для записи
в BRAM. Поэтому слово внутренней очереди и слово результата имеют
разный формат.

Сначала записываются данные, затем заголовок с адресом и длиной.
После подтверждения записи заголовка появляется `DATA_VALID`.
Признак `stop` задаёт `FINAL_PACKET`; при заполнении области ядро
может опубликовать промежуточный фрагмент.

Для текущего вызова драйвер знает ожидаемую длину чтения и ограничивает
её размером области. Данные в BRAM от прошлой операции могут
физически сохраняться, поэтому границами нового результата служат
его длина и свежий признак готовности.

## Формирование SCL

До сих пор мы рассматривали обмен байтами. Чтобы понять, как engine
выполняет его на линиях, нужно различать команду отпустить SCL
и фактический подъём этой линии.

![Делитель SCL и обратная связь от физических линий](../../../figures/architecture/pl-subsystem/i2c/cores/master/timing.svg)

*Рисунок 7. I²C master: формирование SCL.*

На обычных тактах счётчик `div_cnt` переключает разрешение выхода
`scl_oe` через выбранный интервал `divisor`. Сам `scl_o` равен нулю:
включённый выход тянет SCL вниз, выключенный отпускает её. Текущий
драйвер выбирает режим `speed = 0`, номинально 100 кГц в RTL.

Входные уровни проходят через `debouncer` и `sync`. Engine использует
полученные признаки спада `scl_ne` и фронта `scl_pe` для работы с SDA.

![Изменение и выборка SDA относительно фронтов SCL](../../../figures/architecture/pl-subsystem/i2c/cores/master/sampling.svg)

*Рисунок 8. I²C master: изменение и выборка SDA.*

При отправке адреса и данных SDA меняется по спаду SCL, чтобы
к следующему фронту значение было установлено. При чтении SDA
выбирается по фронту SCL. Биты каждого байта идут от старшего
к младшему. Масштаб рисунка условный, задержки фильтра и синхронизации
на нём не показаны.

## Ожидание подъёма SCL

Ведомое устройство может удерживать SCL в нуле после того, как master
её отпустил. На фазе подтверждения ядро ждёт реальный фронт, чтобы
не прочитать ACK раньше времени.

![Отпускание SCL ядром и фактический подъём после удержания ведомым](../../../figures/architecture/pl-subsystem/i2c/cores/master/clock-stretching.svg)

*Рисунок 9. I²C master: ожидание SCL в READ_ACK.*

В `READ_ACK` ядро выдерживает низкий SCL, отпускает линию и ждёт
`scl_pe`. На фронте SDA = 0 означает ACK, SDA = 1 — NACK. Пока
линия удерживается, счётчик `stretch_cnt` продолжает счёт.

При его заполнении устанавливается `ERR_ACK`. Сам переход из
`READ_ACK` всё ещё связан с фронтом SCL, поэтому для завершения
зависшего ожидания драйвер может сбросить ядро. Аппаратный признак
ошибки и программное восстановление здесь дополняют друг друга.

## Завершение и восстановление

Успех операции определяется несколькими условиями, поскольку автомат
шины и запись результата заканчивают работу независимо.

![Независимые признаки завершения шины и готовности результата](../../../figures/architecture/pl-subsystem/i2c/cores/master/completion.svg)

*Рисунок 10. I²C master: признаки готовности.*

`core_state = 0` означает `IDLE`. Для записи этого достаточно при
отсутствии `ERR_ACK`. Для чтения дополнительно требуется свежий
`DATA_VALID`. Признаки `DATA_VALID` и `ERR_ACK` сохраняются до сброса
IRQ. Драйвер проверяет условия и срок ожидания по часам PS.

NACK устройства после адреса или записанного байта означает неуспех
операции. Драйвер сбрасывает ядро и возвращает ошибку без повтора.
Штатный NACK, который сам master выдаёт после последнего прочитанного
байта, такой ошибки не создаёт.

При программном тайм-ауте драйвер восстанавливает ядро и может повторить
попытку в пределах установленного лимита. Повтор означает новый обмен
на физической шине. Подробности условий приведены в таблице ниже.

После успешного чтения драйвер забирает результат, освобождает mutex
и возвращает байты сервису. На этом заканчивается физическая часть
нашего примера. Ведомый сервис получает нужное значение и подготавливает
[ответ внешнему ведущему](slave.md#подготовка-первого-байта-чтения).

Мы разобрали оба аппаратных конца пути I²C. В [главе MDIO](../../mdio/mdio.md)
тот же путь будет рассмотрен для подсистемы с заранее подготовленными
ответами. Оставшиеся разделы этой главы содержат форматы и параметры
для работы с исходниками.

## Форматы команды и результата

Эти сведения позволяют сопоставить описанные действия с содержимым
регистров, FIFO и BRAM.

### Заголовок команды

![Поля заголовка команды master](../../../figures/architecture/pl-subsystem/i2c/cores/master/command-format.svg)

*Рисунок 11. I²C master: заголовок header_t.*

| Поле header_t | Биты | Назначение |
|---|---|---|
| `num_bytes` | `31…11` | Число байтов фазы |
| `speed` | `10…9` | Выбор делителя SCL |
| `restart` | `8` | Связать фазу со следующим заголовком |
| `rw` | `7` | 0 — запись, 1 — чтение |
| `phy_addr` | `6…0` | Семибитный адрес устройства |

Для чтения одного байта регистра `0x10` устройства `0x2A`:

| Порядок в TX FIFO | Слово | Смысл |
|---|---|---|
| 1 | `0x0000092A` | Запись одного байта, `restart = 1` |
| 2 | `0x00000010` | Указатель в младших восьми битах |
| 3 | `0x000008AA` | Чтение одного байта, `restart = 0` |

Для отдельной записи `0x7B` по указателю `0x10` используются заголовок
`0x0000102A` и слово `0x00007B10`. Для отдельного чтения двух байтов —
заголовок `0x000010AA`. Младший байт слова данных передаётся первым.

### Результат в памяти

![Формат опубликованного результата master](../../../figures/architecture/pl-subsystem/i2c/cores/master/memory-format.svg)

*Рисунок 12. I²C master: формат результата в BRAM.*

База — `0x40000000`, `WR_MEM_OFFSET = 0`. Заголовок находится по
смещению `+0x0000`, данные начинаются с `+0x0004`.

| Часть заголовка BRAM | Биты | Содержимое |
|---|---|---|
| Старшие разряды | `31…29` | Нули |
| Длина | `28…7` | 22-битный счётчик `byte_cnt` |
| Адрес | `6…0` | `phy_addr` |

Пример для адреса `0x2A` и пяти байтов `12 34 56 78 9A`:

| Смещение | Слово | Смысл |
|---|---|---|
| `+0x0000` | `0x000002AA` | Длина 5, адрес `0x2A` |
| `+0x0004` | `0x78563412` | Первые четыре байта, B0 в битах `7…0` |
| `+0x0008` | `0x0000009A` | Один полезный байт хвоста |

Область занимает `0x1000` байтов: заголовок и до 4092 байтов данных.
Длина определяет полезную часть последнего слова.

## Параметры и обработка ошибок

TX FIFO имеет глубину 64 слова. Драйвер заполняет его до запуска,
без ожидания освобождения места внутри цикла загрузки. Текущий
`make_header` оставляет `speed = 0`.

| Код speed | Номинальный режим в RTL |
|---|---|
| `00` | 100 кГц |
| `01` | 400 кГц |
| `10` | 1 МГц |
| `11` | 1,5 МГц |

`STRETCH_TIMEOUT_MS` определяет разрядность счётчика `stretch_cnt`.
Время в состоянии `TIMEOUT` engine используется для выдержки
условий STOP и повторного START. Регистр с тем же именем `TIMEOUT`
задаёт отдельную выдержку `tx_data_ctrl` перед возвратом к ожиданию
запуска. В `WAIT_PACKET` счёт `div_cnt` продолжается.

| Событие | Состояние аппаратуры | Действие драйвера |
|---|---|---|
| Запись завершена | `core_state = 0`, нет `ERR_ACK` | Вернуть успех |
| Шина свободна, результат ещё записывается | Engine в IDLE, свежего `DATA_VALID` нет | Продолжать опрос |
| Чтение завершено | Ядро свободно, новый `DATA_VALID`, нет `ERR_ACK` | Забрать результат BRAM |
| NACK устройства | `ERR_ACK`, переход к STOP | Сбросить ядро, вернуть ошибку без повтора |
| Долгое удержание SCL в READ_ACK | `ERR_ACK`; ожидание фронта может продолжаться | Сбросить ядро, вернуть ошибку без повтора |
| Тайм-аут драйвера | Условие завершения не выполнено | Сбросить ядро, повторить в пределах лимита |
| Заполнен TX FIFO или RX FIFO | Признак full и аппаратный IRQ | Отдельной ветви full в `wait_completion` нет |

Восстановление записывает `soft_reset` в CSR и выдерживает 10 мс.
Для повторяемых ошибок предусмотрено до трёх попыток. Ошибка MMIO
также ведёт к восстановлению. Срок ожидания по умолчанию — 100 мс.
`FINAL_PACKET` и признаки empty и full для FIFO отражают текущие
аппаратные сигналы, в отличие от сохраняемых `DATA_VALID` и `ERR_ACK`.
