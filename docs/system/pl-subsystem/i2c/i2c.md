# Подсистема I²C

Теперь пройдём описанный путь на конкретном примере. Пусть внешний
ведущий хочет прочитать регистр `0x10` устройства с адресом `0x2A`,
а затем записать туда `0x7B`. Адрес и значения выбраны для объяснения.
Устройство считается настроенным в профиле BVSTK.

На стороне внешнего ведущего работает `I2C_slave_0`. На стороне
устройства — `I2C_master_0`. Рассмотрим, что связывает их при одном
чтении и что меняется при записи.

## Как ведущий задаёт нужный регистр

В I²C адрес устройства и номер его регистра передаются в разных
местах. Сначала ведущий выбирает устройство адресом `0x2A` с
направлением записи и передаёт байт `0x10`. Затем выдаёт повторный
START, снова выбирает `0x2A`, уже с направлением чтения, и принимает
ответ. Для чтения одного байта он завершает приём NACK и условием STOP.

Байт `0x10` в первой фазе только выбирает регистр. Значения для записи
после него нет. В BVSTK смысл этого байта определяет программный
сервис. Аппаратное ядро видит адрес, направление и последовательность
данных. Если обозначения START, ACK или повторный START пока незнакомы,
их достаточно разобрать в короткой [главе о протоколе](protocol/protocol.md).

## От указателя к окну ответа

Ведомое ядро сохраняет байт `0x10` в BRAM. На границе повторного START
оно публикует фрагмент записи. Программа получает `DATA_VALID`,
читает фрагмент и сохраняет указатель регистра. Запись только указателя
также разрешает последующую подготовку чтения — устанавливает
`read_armed`.

![Доставка события I²C в PS и подготовка ответа ведомого ядра](../../figures/architecture/pl-subsystem/ps-interaction/i2c-irq.svg)

*Рисунок 1. I²C slave: от IRQ к сервису и ответу.*

Приняв адрес с направлением чтения, ядро поднимает `RD_REQUEST`.
Оно удерживает SCL и пока не подтверждает адрес. Это время предназначено
для подготовки первого байта. Если `DATA_VALID` и `RD_REQUEST` пришли
вместе, программа сначала разбирает запись указателя, затем готовит
ответ от `0x10`.

`bvstk_i2c_slave_service` проверяет кэш. Допустим, достоверного значения
регистра пока нет. Тогда он вызывает `bvstk_i2c_master_service`,
который выполняет физическое чтение через драйвер и `I2C_master_0`.
На другом участке шины начинается отдельный обмен: запись указателя
`0x10`, повторный START и чтение одного байта у устройства.

Пусть устройство вернуло `0x34`. При успешном завершении ведущий
сервис сохраняет байт в кэше и возвращает его ведомому сервису.
Код обслуживания заполняет окно ответа BRAM и передаёт `rd_valid`.
Ядро забирает первый байт, отпускает SCL, подтверждает адрес и выдаёт
`0x34` внешнему ведущему. Внешнее чтение завершается на его стороне
после NACK и STOP.

Получились два связанных обмена: внешний запрос и физическое чтение.
Их соединяют сервисы и память. Время подготовки ответа ограничено
удержанием SCL; при опоздании этот успешный сценарий прерывается
аппаратной обработкой ошибки.

## Если значение уже есть в кэше

При повторном обращении сервис может найти достоверный `0x34` сразу.
Тогда ведущее ядро не запускается: из кэша готовится ответ ведомого
ядра. Так повторное чтение на внешней шине может обойтись без
физического чтения устройства.

Сервис собирает окно из последовательных достоверных регистров,
начиная с указателя. Он останавливается на первой недостоверной
записи, границе устройства или пределе окна. Если отсутствует самый
первый байт, физически читается только он, и окно содержит один байт.
Текущие порты выделяют для окна до 64 байтов.

Это связано с устройством самого протокола: ведущий не сообщает длину
чтения заранее. Он подтверждает каждый байт, пока хочет продолжать.
Если подготовленное окно исчерпано, PL запрашивает следующее. Так
программа подготавливает данные частями. Запрос продолжения может
появиться заранее, ещё до подтверждения последнего байта окна.

Указатель сервиса продвигается на длину подготовленного окна.
Поэтому его состояние отражает подготовку данных, а число байтов,
фактически принятых внешним ведущим, определяется отдельно по обмену
на шине. Новая явная запись указателя задаёт начало следующего чтения.

## Запись в тот же регистр

Теперь ведущий выбирает `0x2A` с направлением записи и передаёт два
байта: `0x10`, затем `0x7B`. Сервис трактует первый как номер регистра,
второй — как записываемое значение. Повторный START для этой операции
не нужен.

Ведомое ядро принимает байты и публикует их в BRAM. Затем ведущий
сервис проверяет допустимость регистра, значения и политику записи.
Если операция запрещена, она заканчивается до обращения к устройству.
Уже выданный аппаратный ACK относится к приёму байта и не может
задним числом сообщить об этом отказе.

При разрешении драйвер задаёт `I2C_master_0` запись тех же двух байтов
на стороне устройства. После успешного обмена сервис сохраняет
`0x7B` в кэше. При ошибке физической операции соответствующая запись
кэша становится недостоверной. Следующий ответ внешнему ведущему
подготавливается уже с учётом этого состояния.

## От сценария к реализации

Теперь можно раскрыть аппаратные части, не теряя общий путь запроса.
[Вводная глава о ядрах](cores/cores.md) объясняет их роли и границу
с программой. Затем [slave](cores/slave.md) показывает, как входные
биты становятся запросом к PS и как ответ попадает обратно на SDA.
Глава [master](cores/master.md) продолжает ту ветвь, где для ответа
понадобилось физическое чтение.

Профили и исполнители в обеих ОС разобраны в
[главе о программе PS](../ps-interaction/ps-interaction.md).
Адреса областей приведены в [карте памяти](../reference/reference.md#i²c).
