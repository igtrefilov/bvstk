# Работа с DCP2 и примеры обмена

Скрипт [dcp2_client.py](../../scripts/dcp2/dcp2_client.py) выполняет
одноразовые операции и принимает события. Команды ниже запускаются на
компьютере из корня BVSTK. Структура сообщений, форматы полей и правила
обмена собраны в [главе о кадре](../reference/dcp2/02-frame.md).
Эта глава содержит команды, клиентский код и практические примеры.

Для разработчика собственного клиента:

- [Чтение и изменение политик](#политики-i²c-и-mdio).
- [Кэш устройства и показатели](#кэш-устройства-и-показатели).
- [Использование CACHE из Python](#использование-из-python).
- [Проверка соединения и ошибки DCP2](../reference/dcp2/examples/connection.md).
- [Примеры обмена FS](../reference/dcp2/examples/files.md).

```sh
python3 scripts/dcp2/dcp2_client.py --help
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --ping
```

`--ping` (также `--ping-only`) печатает `PING -> OK` при успешном обмене и
завершается. Это проверка протокольного соединения, не файловой системы.
Порт по умолчанию — `8889`, тайм-аут сокета — 5 секунд; их задают через
`--port` и `--timeout`.

## Кэш устройства и показатели

Получить полный снимок кэша без обращения к физической шине:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --cache-get mdio lan8720
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --cache-get i2c axp15060
```

Подписаться на обновления:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --cache-watch mdio lan8720
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --cache-watch i2c axp15060 --cache-duration 10
```

Клиент собирает все страницы начального снимка, затем применяет изменения.
Каждая строка JSON содержит полный локальный снимок после очередного события.
`--cache-duration` ограничивает время наблюдения в секундах; без него команда
работает до Ctrl+C. Для Python-клиента достаточно стандартной библиотеки.

В `resources` передаются ID ресурсов из профиля, разрядность, достоверность,
происхождение и метка обновления. Значения выводятся шестнадцатеричными строками:
это сохраняет точность 64-битных чисел при передаче JSON другим программам.

Пример одной записи ресурса:

```json
{
  "id": "reg_01",
  "width_bits": 16,
  "valid": true,
  "source": "device",
  "value": "0x0024",
  "updated_ms": 12500
}
```

`valid=false` означает отсутствие достоверного значения. `source=settings`
указывает на начальные данные из настроек. Их нельзя использовать как
подтверждение состояния физического устройства.

При потере событий клиент выводит строку `kind=resync_required` с
`synchronized=false` и автоматически запрашивает новый начальный снимок.
Потребитель должен скрыть прежние показатели до появления согласованного
снимка. При обрыве TCP команда завершается с ошибкой; новый запуск получает
свежее состояние. Закрытие соединения освобождает подписки.

### Расшифровка как во вкладке «Показатели»

В комплекте есть [cache_indicators.mjs](../../scripts/dcp2/cache_indicators.mjs).
Он использует локальные профиль и карту регистров, а также общий с web UI
декодер. Для этого дополнительного шага нужен Node.js. Скрипт выводит
человекочитаемые показатели и расшифрованные поля; браузерный `view.js`
не исполняется.

```sh
set -o pipefail
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --cache-watch mdio lan8720 |
  node scripts/dcp2/cache_indicators.mjs configs/mdio/lan8720/lan8720.json
```

Карта по умолчанию берётся из поля `register_map`, относительно папки профиля.
Её можно указать вторым аргументом:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --cache-get i2c axp15060 |
  node scripts/dcp2/cache_indicators.mjs \
    configs/i2c/axp15060/axp15060.json \
    configs/i2c/axp15060/register_map.json
```

Локальные файлы должны соответствовать рабочему профилю PS. Проверяются цель,
набор ID ресурсов и разрядность; профиль другого устройства не принимается.
Расшифровка поддерживает текущий формат карты регистров I²C и MDIO. Сам сервис
CACHE и Python-клиент принимают имена любых зарегистрированных подсистем.

### Использование из Python

```python
import socket
import sys

sys.path.insert(0, "scripts/dcp2")
from dcp2_cache import CacheClient, CacheResyncRequired, apply_event

with socket.create_connection(("192.168.0.10", 8889), timeout=5) as sock:
    client = CacheClient(sock)
    state = client.snapshot("mdio", "lan8720", subscribe=True)
    print(state["resources"]["reg_01"])
    while True:
        try:
            event = client.event(timeout=1)
        except socket.timeout:
            continue
        try:
            apply_event(state, event)
        except CacheResyncRequired:
            state = client.snapshot("mdio", "lan8720", subscribe=True)
        print(state["revision"], state["resources"]["reg_01"])
```

Один `CacheClient` может обслуживать несколько подписок на одном сокете.
Храните отдельный `state` для каждой и выбирайте его по `subscription_id`
события. Запросы и приём событий выполняются последовательно в одном потоке.
Данные, пришедшие во время запроса другого снимка, сохраняются в очереди клиента.

Двоичный формат и ограничения описаны в [разделе CACHE спецификации DCP2](../reference/dcp2/07-cache.md).
Обычные `READ`, `WRITE`, `NOTIFY` и `STREAM` сохраняют свои форматы.

## Политики I²C и MDIO

Штатный клиент читает действующую политику и редактирует режим и списки.
Сначала получите её текущее состояние. Адрес `0x36` ниже — пример;
используйте адрес и диапазоны из профиля своего устройства.

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --i2c-policy-get 0x36
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --mdio-policy-get 1
```

GET печатает в стандартный вывод один JSON с режимом и массивами
`whitelist`, `blacklist`. Режим — строка `whitelist` или `blacklist`.
Правило I²C содержит числовые `reg` и `val`; у MDIO также есть `mask`.
Снимок можно перенаправить в файл или разобрать собственным скриптом.

Успешное изменение выводит строку вроде `I2C POLICY_ADD -> OK`.
Диагностика событий и ошибки поступают в `stderr`, поэтому не нарушают
JSON. При ошибке клиент завершается с ненулевым кодом. При ненулевом
статусе ответа сообщение содержит шину, операцию и статус, например
`error: MDIO POLICY_DELETE failed: ERR_RANGE`. Ошибки параметров
и соединения сообщают свою причину без статуса DCP2.

Каждый запуск выполняет одну операцию в новом TCP-соединении:

| Действие | I²C | MDIO |
|---|---|---|
| Получить снимок | `--i2c-policy-get ADDR` | `--mdio-policy-get PHY` |
| Выбрать режим | `--i2c-policy-set ADDR MODE` | `--mdio-policy-set PHY MODE` |
| Добавить правило | `--i2c-policy-add ADDR LIST REG VALUE` | `--mdio-policy-add PHY LIST REG VALUE MASK` |
| Удалить правило | `--i2c-policy-delete ADDR LIST REG VALUE` | `--mdio-policy-delete PHY LIST REG VALUE MASK` |
| Очистить список | `--i2c-policy-clear ADDR LIST` | `--mdio-policy-clear PHY LIST` |

`MODE` выбирает действующий режим, `LIST` — редактируемый список.
Оба параметра принимают `whitelist`, `blacklist`, `0` или `1`.
Числовые поля можно записывать десятичными числами или с префиксом `0x`.
Клиент проверяет границы полей протокола до подключения; наличие устройства
и ограничения его профиля проверяет сервер.

ADD, DELETE и CLEAR сохраняют режим. Если выбранный список уже активен,
правка сразу меняет разрешённые записи. Для подготовки нового набора
можно заполнить неактивный список, проверить GET, затем переключить MODE.

У MDIO в ADD и DELETE маска обязательна. Маска `0xFFFF` задаёт точное
значение, `0` — любое значение выбранного регистра. При удалении важны
регистр, маска и биты VALUE, выбранные этой маской.

### Правило I²C

Пусть устройство `0x36` работает в BLACKLIST, а его белый список пуст.
Профиль допускает регистр `0x10` и значение `0x03`. Добавим эту пару
в неактивный белый список и проверим результат:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --i2c-policy-add 0x36 whitelist 0x10 0x03
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --i2c-policy-get 0x36
```

GET должен показать прежний режим `blacklist` и добавленное правило
в `whitelist`. В JSON это `reg=16`, `val=3`. Чтобы включить подготовленный
список, переключим режим и прочитаем его снова:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --i2c-policy-set 0x36 whitelist
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --i2c-policy-get 0x36
```

Теперь разрешена только подготовленная пара. Команды политики меняют
правила сервиса и не выполняют запись регистра устройства.

Для удаления одной пары используйте DELETE:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --i2c-policy-delete 0x36 whitelist 0x10 0x03
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --i2c-policy-get 0x36
```

Другой способ удаления — очистить весь белый список:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --i2c-policy-clear 0x36 whitelist
```

Режим WHITELIST сохраняется. Пустой белый список запрещает записи.

### Правило MDIO с маской

Пусть PHY 1 работает в BLACKLIST, а чёрный список пуст. Добавим правило
для регистра 0 с `VALUE=0xFFFF`, `MASK=0x8000`:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --mdio-policy-add 1 blacklist 0 0xFFFF 0x8000
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --mdio-policy-get 1
```

Сервис сохраняет значимые биты: в добавленном правиле GET покажет
`val=32768`, `mask=32768`, то есть `0x8000`. Оно запрещает записи
с установленным старшим битом регистра 0. Если исходный режим был другим,
чёрный список включается командой `--mdio-policy-set 1 blacklist`.

Удалить это правило можно с нормализованным значением:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --mdio-policy-delete 1 blacklist 0 0x8000 0x8000
```

Вместо удаления отдельных правил список можно очистить целиком:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --mdio-policy-clear 1 blacklist
```

Режим BLACKLIST сохраняется. Пустой чёрный список разрешает все
допустимые записи PHY.
Результат выбранного действия проверяется через `--mdio-policy-get 1`.

### Ошибки и сохранение

Команды изменения отправляются один раз. После таймаута проверьте политику
через GET: операция могла выполниться. Во FreeRTOS правки сохраняются
в памяти; для записи на носитель используются консольные команды
`i2c <имя> save` и `mdio <имя> save`. Вариант Нейтрино и поведение прежней
I²C POLICY_SET описаны в [разделе о сохранении](../reference/dcp2/04-policies.md#рабочая-конфигурация-и-сохранение).
Форматы кадров и ограничения находятся в
[главе о политиках](../reference/dcp2/04-policies.md), конкретные обмены —
в [примерах управления политиками](../reference/dcp2/examples/policies.md).

## Регистры MDIO

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --mdio-read 1 2
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --mdio-read 1 3
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --buses mdio
```

Запись: `--mdio-write PHY REG VALUE` (hex или decimal). Она проходит
ту же политику, что shell и вход ESP32. Не повторяется автоматически;
успех означает отправку кадра без аппаратного подтверждения PHY.
Не используйте произвольные регистры/RESET для безобидной проверки.
Сервис остаётся `0x03`, read/write — `0x00`/`0x01`: переименование
не изменило двоичный формат DCP2.

## Каталоги и файлы FreeRTOS

Сначала получите сведения о доступных томах и ограничениях сервера:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --fs-info
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --fs-stat flash:/config/network.json
```

Рекурсивное перечисление каталога:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --fs-list flash:/config/ --recursive
```

Результат — по одному объекту JSON на строку. `path` содержит путь
относительно заданного корня, `type` — `file` или `directory`, `size` —
размер файла в байтах; для каталога он равен нулю. Это пример формы
результата, а не гарантированный состав устройства:

```jsonl
{"path":"i2c","type":"directory","size":0}
{"path":"i2c/device.json","type":"file","size":512}
```

Без `--recursive` выводятся только непосредственные дети. Этот режим
не читает содержимое файлов. Для одного файла и полного дерева:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --fs-read flash:/config/network.json --output network.json
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --fs-tar flash:/config/ --output config.tar
tar -tf config.tar
```

TAR всегда рекурсивен и включает пустые каталоги. Можно выбрать другой
доступный том, например `--fs-tar sd:/ --output sd.tar`.
В текущем Нейтрино FS не подключён и возвращает `ERR_UNSUPPORTED`;
используйте [SSH-копирование](files.md).

## Результат и обработка ошибок

`--fs-info` и `--fs-stat` выводят JSON. `--fs-list` выводит JSON по строкам.
`--fs-read` и `--fs-tar` без `--output` передают исходные байты в стандартный
вывод; служебные сообщения идут в стандартный поток ошибок. Не выводите
бинарный файл в терминал.

С `--output` клиент создаёт временный файл рядом с целью, а после успешного
окончания чтения и закрытия потока заменяет целевой файл. При ошибке старая
цель сохраняется, временный файл удаляется. Успешная операция перезаписывает
существующую цель. При выводе в стандартный поток результат может быть
частичным; потребитель обязан проверить код завершения процесса.

```sh
if python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
    --fs-tar flash:/config/ --output config.tar; then
  tar -tf config.tar
else
  printf '%s\n' 'Чтение конфигурации не завершено' >&2
fi
```

Встроенные повторы управляются `--fs-retries` (по умолчанию 2).
`--fs-block-size` задаёт размер запрашиваемого блока: штатно 3072 байта,
`0` выбирает максимум сервера. Для проверки повторяемого чтения блока:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --fs-tar flash:/config/ --output config.tar \
  --fs-block-size 513 --fs-verify-repeats
```

Клиент повторно запрашивает каждый блок, включая последний, и сравнивает
байты. Это проверка протокольного повтора, не атомарности дерева. На время
копирования исключите параллельную запись; при изменении исходника начните
новое чтение. Актуальные лимиты путей, глубины и дескрипторов узнают из
`--fs-info` и спецификации, не из предположения о версии скрипта.

## Уведомления управления

Без одноразовой операции скрипт подключается, выполняет PING, подписывается
на NOTIFY и печатает события до остановки команды:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --buses i2c
```

По умолчанию выбраны все классы, источники `telnet,host,dcp,internal,web`,
шина `i2c` и отметка времени. Фильтры сужают наблюдение:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --classes attempt,commit,denied --sources telnet,host --buses i2c
```

`--no-timestamp` отключает запрос времени. `--snapshot` передаёт флаг
подписки, но текущий сервер не формирует отдельный снимок состояния.
Попытка записи не равна её выполнению; смотрите класс, статус и последующее
событие завершения. Для проверки изменения используйте заранее выбранный
безопасный регистр и допустимое для оборудования значение.

## Реальные наблюдения I²C и MDIO

NOTIFY обслуживает обе подсистемы, STREAM передаёт наблюдения из того же
журнала RAM, что используется вкладками web UI. Подписки начинают выдачу
с текущего конца журнала, не с архивной истории:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --buses i2c,mdio
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 --stream i2c --stream mdio
```

Команды запускаются по очереди: сервер DCP2 обслуживает одно TCP-соединение.
Web может наблюдать одновременно и не потребляет записи подписки DCP2.
Включение источника через shell не требуется. Сбор всегда активен для
доступных I²C и MDIO сервисов, подписка не включает опрос регистров.
SPI и UART пока имеют только тестовый источник.

Клиент декодирует записи `BVT1`, показывает источник, тип, адрес, регистр,
значение и статус. STREAM использует тот же подтверждённый журнал, что и
web UI: служебные пробы и обмены с неподтверждёнными профилями не выдаются.
`SLAVE_REPLY_PREPARED` — подготовка ответа I²C, не подтверждённые байты на
проводе. `MASTER_READ` с ошибкой не имеет достоверного значения.
`CAPTURE_WRITE` — запись, которую успел увидеть PS у подтверждённого профиля;
потерянные в PL кадры восстановить невозможно. Кэш MDIO не сообщает PS
каждый факт чтения внешним мастером.

При переполнении RAM STREAM выставляет `overflow=1` и `lost_delta`;
NOTIFY передаёт `SOFTWARE_LOSS` с числом записей в `arg0`.
Уведомление о потере доставляется для выбранной шины независимо от
фильтров классов и источников. Это потери записей программного журнала,
не точное число потерянных физических транзакций. Время — системный тик PS.
Для старого сервера без источника Web используйте явно
`--sources telnet,host,dcp,internal`.

## Тестовые потоки

Во FreeRTOS консоль может включить детерминированный источник, не
обращающийся к MMIO:

```text
i2c stream fake enable 100 counter 4
i2c stream fake status
```

На компьютере:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --stream i2c --stream-flags raw,timestamp,reset-lost
```

Параметр `--stream` повторяется для нескольких шин: `i2c`, `mdio`, `spi`,
`uart`. Источники выключены после перезапуска и не сохраняются в QSPI.
После проверки отключите включённый источник командой
`i2c stream fake disable` либо аналогичной командой другой шины.

Шаблоны, периоды и ограничения источников описаны в
[справочнике консоли](../reference/console-commands.md#тестовые-потоки).
Они проверяют доставку тестовых данных даже для выключенного физического
ядра. Клиент помечает такие события `synthetic=1`; это не перехваченный
трафик. На I²C и MDIO тестовый и реальный источники могут передаваться
одновременно, но имеют разные флаги и форматы данных.

## Диагностический MEM

Скрипт умеет читать и записывать память через `--mem-read` и `--mem-write`;
`--width` задаёт разрядность, `--count` — число читаемых элементов,
`--autoinc` — увеличение адреса. В текущем FreeRTOS этот путь допускает
сырой доступ к 32-битному адресному пространству. Даже чтение неверного
адреса может остановить устройство. Поэтому произвольные адреса не
используются как проверка соединения; применяйте PING.

Пример только для заранее проверенного читаемого регистра I²C master:

```sh
python3 scripts/dcp2/dcp2_client.py 192.168.0.10 \
  --mem-read 0x43c00000 --width 32
```

Запись проходит ниже политики I²C и может рассогласовать сервис с
оборудованием. Адрес, допустимое значение и исключение конкурентного
доступа проверяют по [контракту платы](../reference/board.md) и драйверу.

Поля запросов и ответов показаны в [примере MEM](../reference/dcp2/examples/memory.md).
