# Устройства и политики


## Правила запросов

Поддерживаются GET и PUT. Неподдерживаемый метод получает 405,
неизвестный маршрут — 404. Параметры передаются в query с URL-кодированием;
повторяющийся запрашиваемый ключ, неверная percent-последовательность,
NUL, управляющий символ или переполнение буфера отклоняются. Числа в query
десятичные, неотрицательные, без суффиксов.

JSON передаётся в UTF-8. Успех действия — HTTP 200 и `{"ok":true}`,
если ниже не описаны дополнительные поля. Ошибка — соответствующий
HTTP-код и `{"ok":false,"error":"описание"}`. Списки и снимки читаются
без обязательного поля `ok`. Ошибка перечисления каталога после начала
ответа указывается внутри тела; проверяйте `ok` и полноту JSON.

Сервисные ошибки: 400 — неверные данные или диапазон; 403 — отказ политики;
404 — неизвестное устройство; 423 — занято; 503 — сервис не готов;
504 — тайм-аут сервиса; 500 — прочие ошибки. Все ответы запрещают
кэширование. Аутентификации, TLS и атомарных транзакций между клиентами нет.

## Подсистемы

`GET /api/ui/bus?bus=i2c` или `bus=mdio` возвращает:

```json
{"ready":true,"devices":[{"name":"lan8720","address":1,"available":true,"presence":"responding","policy":"whitelist"}]}
```

Для конкретного устройства добавляется `name`:

```text
GET /api/ui/bus?bus=mdio&name=lan8720
```

| Поле | Смысл |
|---|---|
| `config` | Совместимая проекция настроек RAM в прежнем формате API, не документ профиля v2 |
| `revision` | Восемь hex-символов, FNV-1a 32 бит от канонического JSON |
| `saved` | `true`, если снимок совпадает с сохранённым конфигом; `false`, если нет; `null`, если прочитать состояние не удалось |
| `file_name` | Относительный путь в `flash:/config/i2c/` либо `flash:/config/mdio/`: например `lan8720/lan8720.json`; старые `lan8720/profile.json` и `lan8720.json` принимаются для миграции |
| `register_map` | Имя карты рядом с профилем, пустая строка при отсутствии |
| `view` | Имя JS-формы рядом с профилем, пустая строка при отсутствии |
| `available` | `true` только при `presence=responding`; не просто наличие профиля |
| `presence` | `unknown`, `responding` или `unavailable`; то же поле есть в списке устройств |
| `cache` | Кэш I²C или MDIO: массив `reg`, `val`, `valid`, `source`, `updated_ms` |
| `stats` | Только MDIO: общие счётчики `reads`, `writes`, `denied`, `errors`, `observed` |

`register_map` и `view` — метаданные [пакета устройства](../device-package/device-package.md),
а не поля совместимой `config`. Действия `apply` и `save` сохраняют их.
Файлы получает браузер через обычный `GET /api/ui/file` из тома Flash;
PS не выполняет JS и не расшифровывает физические битовые поля.

Источники кэша — `settings` для начальных значений, `I2C` для успешного
физического обмена I²C и `PHY` для обмена с PHY по MDIO. `valid=false`
означает, что достоверного значения для регистра нет; при этом `val` —
только незначащее заполнение. `updated_ms` — монотонная метка в миллисекундах
с момента запуска PS, зафиксированная при последнем обновлении записи; для
недостоверной записи передаётся ноль.

Для фонового обновления без чтения конфигурации используется лёгкий запрос:

```text
GET /api/ui/bus?bus=i2c&name=axp15060&action=cache
GET /api/ui/bus?bus=mdio&name=lan8720&action=cache
```

Он возвращает `cache` и, для MDIO, `stats`. Запрос только снимает текущий
кэш PS и не выполняет физические операции на шине. Web-интерфейс вызывает
его примерно раз в 500 мс на открытой вкладке **Регистры**.

Счётчик `stats.errors` учитывает ошибки реального чтения, записи и
аппаратного подтверждения. Неудачные фоновые проверки наличия PHY не входят
в него: отсутствие устройства — ожидаемый результат зондирования, а не ошибка
обмена с подтверждённым PHY.

Файлы устройств используют v2, но этот API сохраняет поля `name`,
`reg_count`, `policy`, `whitelist`, `blacklist`, `settings` и параметры
соответствующей шины. `apply` принимает эту проекцию и сохраняет метаданные
и ID ресурсов v2, которые редактор не показывает. `save` записывает v2
через ConfigStore; старое несовместимое имя сохраняется в прежнем формате.
`saved` сравнивает нормализованные настройки этой проекции, а не байты
файла и не отображаемые метаданные `device`.

У I²C `unknown` означает отсутствие подтверждённого обмена после старта
или смены адреса. Успешное физическое чтение переводит состояние в
`responding`, ошибка обмена (включая NACK и тайм-аут) — в `unavailable`.
Кэш, начальные `settings`, отказ политики и успешная запись без чтения
не подтверждают присутствие. Это результат последнего обмена, не фоновое
обнаружение отключения устройства. Запрос списка сам не сканирует шину.
У MDIO `responding` требует достоверных ID PHY в регистрах 2 и 3,
прочитанных с оборудования менее трёх секунд назад; иначе `unavailable`.
В старой прошивке I²C поле `available` означало готовность сервиса:
без поля `presence` новый интерфейс считает ответ I²C непроверенным.

`observed` — обработанные входные ячейки, не доказанное число всех кадров
на проводах. Независимые снимки кэша, счётчиков и конфигурации не образуют
одного аппаратно-атомарного снимка.

PUT использует тот же путь и параметры `bus`, `name`, `action`:

| `action` | Дополнительные параметры | Действие |
|---|---|---|
| `apply` | `revision` | Полная конфигурация JSON в теле; применение только в RAM |
| `save` | `revision` | Явное сохранение текущего снимка через ConfigStore |
| `read` | `reg` | Физическое чтение; ответ `ok`, `reg`, `val` |
| `write` | `reg`, `val`, `confirm=true` | Запись с проверкой политики; без сохранения во Flash |
| `invalidate` | Нет | Только MDIO: сброс достоверности кэша |

Для действий без конфигурационного тела отправляйте PUT без тела
(допускается `Content-Length: 0`). Не добавляйте формальное `{}`:
обработчики запросов с параметрами в URL не потребляют это тело, а закрытие
lwIP-сокета с непрочитанными данными может оборвать ответ. Это относится
также к командам `/api/ui/files`; `apply` и загрузка файла требуют тела.
Тело `apply` — не более 32767 байт, без NUL. Переполнение отклоняется
с 413, неполное или некорректное тело — с 400. Для I²C обязательны все
восемь полей штатного формата: `name`, `addr_7b`, `reg_count`,
`max_value_code`, `policy`, `whitelist`, `blacklist`, `settings`.
Неизвестные корневые поля, повторные ключи и некорректная грамматика
отклоняются. MDIO использует свой строгий штатный кодек. Диапазоны и
семантика перечислены в [конфигурации](../configuration/configuration.md).

Имя и число регистров устройства неизменны. У I²C через этот API также
не меняются `max_value_code` и начальные `settings`. Занятый другим
устройством адрес I²C отклоняется с 409. Изменение политики не выполняет
физические записи настроечных регистров.

Перед `apply` и `save` проверяется `revision`. Перед применением проверка
повторяется после чтения тела. Несовпадение даёт 409 без применения
переданного черновика. Это оптимистическая проверка по 32-битному хешу,
не криптографический идентификатор и не атомарный compare-and-swap с shell
или DCP2. Между последней проверкой и применением возможна параллельная
смена конфигурации. Для согласованного редактирования нужен один писатель.
После действия перечитайте снимок и поле `saved`.

Запись I²C синхронизирует RAM-модель; Flash меняется только по `save`.
Успешная запись MDIO означает передачу кадра, не подтверждение PHY.
Чтение может иметь побочные эффекты у latch и read-clear регистров.


## Совместимые маршруты прежнего интерфейса

Для новых клиентов используйте семейство `/api/ui/bus`. Следующие маршруты сохранены и имеют собственную форму запросов.

## GET /api/i2c

Без `name` ответ содержит `ready` (логическое), `count` (число
устройств) и `devices` (массив). Каждая запись имеет:

| Поле | Тип и смысл |
|---|---|
| `name` | Строка, имя устройства |
| `addr_7b` | Целое, 7-битный адрес |
| `file_name` | Строка, имя конфигурационного файла |
| `policy` | Строка `whitelist` или `blacklist` |
| `settings_len`, `whitelist_len`, `blacklist_len` | Целые, длины соответствующих массивов |

С `name` обработчик предназначен для ответа с полями `ready` и
`device`; вложенный объект содержит `name`, `addr_7b`, `file_name`,
`policy`, `whitelist`, `blacklist` (массивы пар `reg`/`val`).
`settings`, `reg_count` и `max_value_code` он не возвращает.

Для неизвестного имени возвращается 200 с
`{"ready":...,"error":"unknown device"}`, а не 404. Полный снимок
конфигурации и состояние сохранения доступны через `/api/ui/bus`.

## PUT /api/i2c

| Поле | Тип | Условие |
|---|---|---|
| `name` | Строка | Обязательно, существующее устройство |
| `policy` | Строка | Необязательно; `whitelist` или `blacklist` |
| `whitelist` | Массив `{reg,val}` | Необязательно; заменяет целиком соответствующий список |
| `blacklist` | Массив `{reg,val}` | Необязательно; заменяет целиком соответствующий список |

Отсутствующее поле сохраняет прежнее значение, пустой массив очищает
список. Адрес, имя, число регистров и `settings` этим запросом не
редактируются. Используйте [пределы конфигурации](../configuration/configuration.md);
дополнительно весь HTTP-документ должен помещаться в 2047 байт.

Ответ 200 содержит `ok:true` и `saved:false`: изменяются работающий сервис
и модель RAM, файл не записывается. Для постоянного сохранения служит
`i2c <sel> save` в shell. `saved:false` здесь означает отложенное сохранение,
а не ошибку применения. 503 — `config_store not ready`; 400 — пустое тело,
отсутствующее имя, неверная политика или массив; 404 — `unknown device`;
500 — `set failed`. Не следует считать 500 гарантией отсутствия всех
частичных изменений предыдущих шагов.

## Диагностические операции I²C

Оба PUT-маршрута выбирают устройство непустым `name` (строка) либо
`addr_7b` (целое `0..127`). Если присутствуют оба, имя имеет приоритет.
`reg` обязателен, целое `0..255`, дополнительно ограничивается моделью
устройства. Для write обязателен `val`, целое `0..255`, дополнительно
проверяются `max_value_code` и политика.

Read возвращает 200 с `ok:true`, `name` (строка), `reg` и `val`
(целые). Write возвращает только `{"ok":true}`. После записи
синхронизируется модель без отдельного сохранения; это не подтверждение
записи JSON в QSPI.

400 — отсутствующее/неверное поле; 404 `device not found` возможен и
при неготовом сервисе; 500 `i2c read failed` — ошибка чтения.
Текущий write отображает любой неуспех сервисной записи в 403 `DENIED`,
в том числе не только отказ политики. По одному этому ответу нельзя
достоверно установить внутреннюю причину. Вызов сервиса использует 100 мс,
но это не гарантия общего времени HTTP-запроса.

## MDIO

Подсистема управляется через `/api/ui/bus?bus=mdio`, shell и MDIO-сервис
DCP2. HTTP использует тот же штатный сервис, кэш и политику; отдельный
black-box драйвер не создаётся. См. [API веб-интерфейса](devices.md).
Конфиги доступны как обычные файлы `flash:/config/mdio/`.
