# Пакет устройства и показатели

Один экземпляр устройства — одна папка. Все аппаратные настройки остаются
в [профиле v2](device-profile-v2.md), описание физических регистров —
в отдельной карте. Индивидуальный скрипт задаёт компоновку вкладки
**Показатели**, не логику драйвера.

```text
flash:/config/
  i2c/
    axp15060/
      axp15060.json
      register_map.json
      view.js
    pca9536/
      pca9536.json
  mdio/
    lan8720/
      lan8720.json
      register_map.json
      view.js
    dp83848c/
      dp83848c.json
    ksz8081rna/
      ksz8081rna.json
```

Исходные пакеты находятся в `configs/`. Для LAN8720A подготовлены
[профиль](../../configs/mdio/lan8720/lan8720.json),
[карта](../../configs/mdio/lan8720/register_map.json) и
[форма](../../configs/mdio/lan8720/view.js).
Для AXP15060 подготовлены [профиль](../../configs/i2c/axp15060/axp15060.json),
[карта](../../configs/i2c/axp15060/register_map.json) и
[форма](../../configs/i2c/axp15060/view.js).
У остальных устройств пока только профили, без выдуманной расшифровки.
Дополнительные файлы можно добавить независимо от пересборки PS.

## Связь файлов и совместимость

В корневом файле `<имя>/<имя>.json` задаются необязательные поля:

```json
"register_map": "register_map.json",
"view": "view.js"
```

Имена относятся к папке профиля, а не к `www`. Путь, `..`, URL и
подкаталоги запрещены. Основа имени состоит из ASCII-букв, цифр, `_`, `-`.
Расширения — `.json` и `.js`. Имя карты — `register_map.json` либо
имя с окончанием `_register_map.json`; максимум 63 символа. `view`
можно опустить: останется стандартная сводка по карте и расшифровка битов.
Без карты вкладка сообщает об отсутствии описания, а не опрашивает шину.

Имя папки — 1–31 ASCII-символ из букв, цифр, `_`, `-`; рекомендуется
совпадение с `id`. Канонический профиль имеет путь
`<папка>/<папка>.json`. Загрузчик также принимает старый
`<папка>/profile.json` и плоский `config/<шина>/<имя>.json` для миграции;
при наличии нескольких вариантов канонический файл имеет приоритет.
Загрузчик не сканирует вложенные подпапки и не воспринимает прочие файлы
пакета как устройства.
Ошибочный новый профиль не заменяется старой копией или умолчаниями.
В FreeRTOS основной `config/` имеет приоритет над старым `configs/`.
Сохранение использует канонический путь `<имя>/<имя>.json`.
Замена профиля в FreeRTOS сохраняет предыдущий файл как `<имя>.json.bak`;
после прерванной замены он восстанавливается при следующем старте.

Генератор встроенных конфигураций включает только `<имя>.json` (старый
`profile.json` остаётся допустимым источником при миграции).
Карта и JS **не встраиваются в ELF** — их нужно установить во Flash.
В Нейтрино папки поддерживает загрузчик I²C; HTTP UI и загрузчик MDIO
в штатной сборке этой ОС отсутствуют.

## Источник данных

Вкладка делает только `GET action=cache` через общий HTTP-канал,
примерно раз в 500 мс при видимой странице. Физических команд шине
нет; переход на вкладку не меняет список автоопроса. Подробный снимок
профиля обновляется обычным механизмом UI. Карта и скрипт загружаются
один раз при открытии вкладки; после изменения файлов её нужно открыть заново.

Обновляются текстовые значения, а не вся форма: раскрытые регистры,
позиция прокрутки и локальное состояние формы сохраняются.
Каждый показатель имеет метку времени с начала работы системы.
Для составного показателя используется самая ранняя метка участвовавших
регистров. Это **не атомарный снимок** и не время открытия страницы.

`valid=false`, отсутствие регистра и значения с источником `settings`
дают **Нет данных**. Умолчания после сброса не подставляются вместо кэша.
Неописанный код отображается как **Не описано** вместе с исходным hex-кодом.
При потере связи остаётся последний снимок с явным предупреждением.
При отсутствии готовности устройства старые кэшированные значения
помечаются как данные последних взаимодействий, а не как текущая готовность.

## Формат карты регистров, версия 1

Карта — JSON UTF-8, максимум 65536 байт. Неизвестные поля и неправильные
типы отклоняются целиком. Выражения JavaScript, функции и `eval` в карте
не поддерживаются. Комментарии и завершающие запятые недопустимы.
Не используйте повторяющиеся ключи: стандартный JSON-парсер браузера
оставляет последнее значение, а не диагностирует повтор.

### Корень

| Поле | Значение |
|---|---|
| `schema_version` | Число `1`, независимо от версии профиля |
| `kind` | Строка `register_map` |
| `id` | ID карты, `[a-z][a-z0-9_]*`, до 64 символов |
| `device` | Непустое название модели |
| `bus` | `i2c` или `mdio`, должно совпасть с профилем |
| `width_bits` | `8` для I²C, `16` для MDIO |
| `register_count` | 1–256 для I²C, 1–32 для MDIO; ровно как в профиле |
| `source` | Объект с непустыми `title`, `document`, `revision`, `url`; URL начинается с `https://` |
| `notes` | Общее пояснение об интерпретации |
| `identity` | Необязательный список из 1–16 условий проверки модели |
| `registers` | По одному описанию для каждого адреса от 0 до `register_count-1` |
| `summary` | 1–64 показателя сводки |

Строковые подписи и пояснения ограничены 600 символами, если для поля
не указан другой предел. ID регистров, полей и показателей используют
тот же шаблон, что ID карты. Адреса и сравниваемые коды — неотрицательные
целые числа либо строки `0x...` в допустимой разрядности.

### Описание регистра

| Поле | Значение |
|---|---|
| `id` | Уникальное имя внутри карты, например `bsr` |
| `address` | Адрес, например `"0x01"` |
| `name` | Краткое обозначение из документации |
| `label` | Подпись в интерфейсе |
| `section` | Раздел и страницы источника |
| `reserved` | Необязательный boolean, по умолчанию `false` |
| `note` | Необязательное пояснение |
| `fields` | 1–32 битовых поля, без пересечений и пропусков |

Все биты, включая резервные, должны быть описаны. Зарезервированные
адреса тоже перечисляются, но имеют только поля `type=reserved`,
`access=none`. Наличие адреса в карте не даёт разрешения на его чтение.

### Битовое поле

| Поле | Значение |
|---|---|
| `id`, `label` | Уникальный в регистре ID и подпись |
| `lsb`, `width` | Номер младшего бита от 0, длина от 1; без выхода за разрядность |
| `type` | `enum`, `uint`, `hex`, `reserved` |
| `access` | `ro`, `rw`, `wo`, `none`; сведения из datasheet, не изменение политики |
| `reset` | Текст: число, `MODE straps`, `unspecified`, `silicon revision` и т. п.; справочно |
| `values` | Только для `enum`, обязательно; объект код → `{label, tone?}` |
| `attributes` | Необязательный список атрибутов из таблицы ниже, не более 8 |
| `note` | Необязательное пояснение |
| `unit` | Необязательная единица измерения, до 40 символов |
| `scale`, `offset` | Только для `uint`, конечные числа; умолчания `1` и `0` |
| `ranges` | Только для `uint`, 1–32 диапазона пересчёта; вместо общих `scale` и `offset` |
| `write_value` | Необязательный фиксированный код для записи, только справочная информация |

Значение извлекается по `lsb` и `width`; для `uint` выводится
`код × scale + offset`, затем `unit`. `hex` сохраняет hex-представление.
Поля `wo` не расшифровываются по прочитанному кэшу.

Для ступенчатых шкал и ограниченного диапазона кодов используется `ranges`:

```json
"type": "uint",
"unit": "мВ",
"ranges": [
  {"min": 0, "max": 70, "scale": 10, "offset": 500},
  {"min": 71, "max": 87, "scale": 20, "offset": -200}
]
```

Границы `min` и `max` включаются в диапазон и укладываются в разрядность
поля. Диапазоны идут по возрастанию, без пересечений. `scale` и `offset`
в каждом диапазоне обязательны и конечны; итог пересчёта тоже должен быть
конечным. Формула использует исходный код: `код × scale + offset`, не
смещение от `min`. За пределами перечисленных диапазонов выводится
«Не описано», без экстраполяции и ограничения к ближайшему значению.
Совместное использование `ranges` и общих `scale` или `offset` запрещено.
Для таких карт нужен фронтенд с поддержкой `ranges`; старая версия
отклоняет неизвестное поле целиком.

`values` содержит до 256 записей. Ключи — десятичные строки без ведущих
нулей, например `"0"`, `"6"`, не `"0x06"`. `label` обязателен.
`tone` — `ok` (зелёный), `bad` (красный), `warn` (предупреждение),
`offline` (обычный текст, умолчание) или `unknown` (серый).
Неописанный код не заменяется ближайшим допустимым.

| Атрибут | Значение |
|---|---|
| `latch_low` | Сохраняется факт нуля до чтения |
| `latch_high` | Сохраняется факт единицы до чтения |
| `read_clear` | Физическое чтение очищает поле |
| `self_clear` | Самосброс |
| `nasr` | Программный сброс не меняет поле |
| `write_one_clear` | Запись единицы очищает |
| `write_any_clear` | Любая запись очищает |

Атрибуты показывают семантику, но не инициируют операции и не эмулируют
изменение регистра. Кэш чтения latch-high — историческое наблюдение,
не доказательство того, что условие активно в момент просмотра.

### Условия и показатели

Условие имеет ровно два поля:

```json
{"field": "bsr.link", "equals": 1}
```

Ссылка — `<id регистра>.<id поля>`; резервные поля не используются.
Список условий соединяется логическим И. Нет значения в кэше — условие
неизвестно, а не ложно. `identity` использует такой же список.
Несовпадение идентификатора блокирует сводку, но оставляет сырые данные
и подробную расшифровку с предупреждением. Если ID не прочитан, это явно
указывается; доступные поля можно рассматривать как данные по выбранной карте.

Простой показатель:

```json
{"id":"link","label":"Связь","field":"bsr.link","note":"По последнему чтению"}
```

Обязательны `id`, `label` и либо `field`, либо `cases`. Необязательны
`note` и переопределение `values` для поля. `cases` — от 1 до 32 вариантов;
порядок значим. Каждый вариант содержит `when` (1–16 условий) и либо
`field` с необязательной `values`, либо фиксированные `label` и `tone`.
Выбирается первый совпавший вариант. Неизвестная более ранняя зависимость
даёт «Нет данных»; перебор не переходит к предположительному результату.
Если все варианты ложны, выводится «Не определено».

## API индивидуальной формы, версия 1

`view.js` — самостоятельный JS-файл UTF-8 до 65536 байт, без `import`
и внешних зависимостей. Он регистрирует объект:

```js
window.bvstkView = {
  apiVersion: 1,
  mount(root) {
    this.value = document.createElement("p");
    root.append(this.value);
  },
  update(snapshot) {
    const link = snapshot.summary.find(item => item.id === "link");
    this.value.textContent = link?.label || "Нет данных";
  }
};
```

`mount` вызывается один раз, `update` — при поступлении снимков.
При смене вкладки уничтожается весь iframe, включая таймеры формы.
Форма может создавать собственные HTML, CSS, SVG, группировку, шкалы и
диаграммы; состояние между обновлениями хранит сама. Изменяйте значения
в существующих элементах, не пересоздавайте интерактивную форму на каждом
снимке. Строки из данных вставляйте через `textContent`.

| Поле `snapshot` | Значение |
|---|---|
| `api_version` | `1` |
| `device` | `id`, `bus`, `presence` (`responding`, `unavailable`, `unknown`) |
| `stale` | Нет свежего ответа HTTP; последний снимок сохранён |
| `identity` | `true`, `false` или `null` (неизвестно либо проверка не задана) |
| `map` | Проверенная карта целиком |
| `cache` | Последний массив кэша API: `reg`, `val`, `valid`, `source`, `updated_ms` |
| `fields` | Объект по ключу `register.field` с расшифрованными полями |
| `summary` | Показатели; `id`, `title` (название), `label` (результат), `status`, `tone`, `updated_ms`, необязательные `raw` и `note` |

У результата поля есть `status`: `known`, `unknown`, `missing` либо
`reserved`; `label`, `tone`, `raw` и `updated_ms`. При наличии реального
значения поле также содержит числовой `value`. Для отсутствующих данных
`raw` и метка равны `null`. Цвет не является результатом операции шины.

Форма работает в iframe с `sandbox="allow-scripts"`, без
`allow-same-origin`. CSP блокирует запросы сети, формы, внешние ресурсы;
доступа к DOM основного UI, Flash API и функциям операций шины нет.
Родитель принимает только сообщения готовности, высоты и ошибки,
проверяя источник и идентификатор экземпляра. В форме нет API команд.
Это всё же исполняемый код: устанавливать следует проверенные скрипты.
Sandbox не гарантирует защиту от расхода CPU/памяти ошибочным скриптом.
Ошибка или отсутствие скрипта возвращает стандартную сводку по карте;
ошибка карты блокирует расшифровку, но не остальные вкладки устройства.

## LAN8720A

Основание — официальный
[Microchip DS00002165C, 2024](https://ww1.microchip.com/downloads/aemDocuments/documents/UNG/ProductDocuments/DataSheets/LAN8720A-LAN8720Ai-Data-Sheet-DS00002165.pdf),
раздел 4.2, страницы 42–51; MODE дополнен таблицей 3-4.
Описаны 14 реализованных регистров, 18 резервных адресов, все 512 бит
адресного пространства как 119 полей. Зарезервированным состояниям
не присвоены выдуманные значения.

Сводка содержит Link, скорость, дуплекс, автосогласование, питание,
энергосбережение, изоляцию RMII, режимы петли, выбор MDI/MDIX, сигнал,
диагностические признаки, адрес и ревизию. При автосогласовании скорость
берётся из HCDSPEED только при подтверждённых Link и завершении согласования;
при принудительном режиме — из BCR. Зарезервированные HCDSPEED не угадываются.
Link=0 у latch-low не отличает текущий обрыв от уже восстановленной линии.
Бит ручного MDI/MDIX не выдаётся за фактический выбор автоматики.
ID-регистры в источнике обозначены R/W: проверка модели не является
криптографической проверкой устройства.

Карта не расширяет автоопрос. Если некоторые показатели пока имеют
«Нет данных», нужные регистры должны попасть в кэш штатным взаимодействием
или явно разрешённым чтением. Просмотр вкладки сам этого не делает.

## AXP15060

Основание — официальный X-Powers
[AXP15060 Datasheet V0.1 от 2018-04-10](https://files.pine64.org/doc/datasheet/star64/AXP15060%20datasheet%20V0.1.pdf),
копия документа на сервере PINE64. Разделы 9.1–9.4, страницы 21–25,
и 10.1–10.2, страницы 26–37. SHA-256 использованного PDF:
`ab57ea9b527cf45e442b7fc5cc9eec4cc9d8ae0d039ba6ee1a718a2d7fc7515f`.

Карта охватывает 74 адреса `0x00–0x49`: 41 описанный регистр и 33 адреса,
отсутствующих в открытой таблице. Все 592 бита представлены 190 полями.
Неописанные адреса отмечены защитным `reserved=true`; им не приписаны
назначение, идентификатор чипа или допустимый доступ. Проверка `identity`
не задана: datasheet не описывает доступный для чтения ID.

Форма показывает 22 управляемых выхода: DC-DC, ALDO, BLDO, CLDO, CPUSLDO
и ключ DC1SW. В отдельные группы вынесены причины включения, настройки
защит, режимы GPIO, маски и флаги IRQ, параметры пробуждения и кнопки POK.
RTCLDO не получает выдуманного регистра или индикатора готовности.

- Напряжение — **задание по регистру**, не измерение. Разрешённый канал
  не доказывает наличие питания; защита и назначение вывода тоже влияют
  на выход. Числовых измерений тока и температуры в открытой карте нет.
- DCDC2–4 и DCDC5 используют двухступенчатые шкалы. Неописанные коды
  не продолжают шкалу и не заменяются максимальным напряжением.
- В двухфазных парах DCDC2 и DCDC3, DCDC4 и DCDC6 сводка использует
  настройки ведущего. При неизвестном режиме зависимые показатели
  остаются неизвестными; собственные регистры видны в подробной расшифровке.
- CPUSLDO с кодом `0x0F` означает слежение `VDDR/2`, не 1450 мВ.
  Для GPIO1 и GPIO2 высокий уровень имеет отдельные ограничения
  1,25–3,3 В; код LDO сам по себе не подтверждает уровень вывода.
- Флаги `0x48` очищаются записью единицы **или восстановлением параметра**;
  флаги `0x49` — записью единицы. Это не read-clear. Маски влияют на
  регистрацию. API кэша I²C не различает чтение и запись: единица после
  команды очистки не подтверждает событие. Форма поэтому подписывает
  результат «Отмечено в кэше», а не заявляет текущую аварию.
- Значения после сброса справочные: документ допускает разные исполнения
  и настройку DC5SET. Таблица исходных выходов в §9.2 отличается от
  умолчаний регистров в §10.2; карта использует последние и не подставляет
  никакие умолчания вместо реального кэша.

Пакет требует обновления фронтенда с поддержкой диапазонов `ranges`.
PS, уже поддерживающий пакеты, менять для интерпретации AXP15060 не нужно.
В существующий сохранённый профиль добавляют только `register_map` и
`view`, сохраняя адрес, правила, ограничения записи и `cache_seed`.
Работа вкладки не расширяет профиль, не меняет опрос и не выполняет
физических операций, в том числе очистки IRQ.

## Установка на существующую плату

1. Собрать и загрузить PS с поддержкой пакетов. Старые версии загрузчика
   не понимают `register_map` и `view`. PL изменять не требуется.
2. Загрузить основной фронтенд: `python3 web/upload_flash_www.py <адрес>`.
3. Сохранить настройки нужного устройства командой `mdio lan8720 save`
   (для I²C — соответствующей командой `i2c`). Скачать резервную копию
   существующего профиля из `flash:/config/`.
4. Через раздел «Файлы» создать папку `flash:/config/mdio/lan8720/`.
   Добавить в **копию сохранённого** профиля только `register_map` и `view`,
   записать её как `<имя>/<имя>.json`. Не заменять работающую политику
   умолчаниями из репозитория. Для остальных устройств достаточно
   перенести сохранённый профиль в их папки, не добавляя ссылки на чужую карту.
5. Загрузить `register_map.json` и `view.js` из пакета LAN8720 рядом с профилем.
   До перезапуска не менять и не сохранять конфигурацию из другой сессии:
   RAM ещё использует старое расположение. Старый плоский файл можно оставить
   как резервную копию — после старта он уступает новому профилю.
6. Перезапустить PS, проверить `mdio lan8720 info`, открыть
   `#mdio?name=lan8720&tab=indicators`. В API `file_name` должен быть
   `lan8720/lan8720.json`, ссылки — `register_map.json` и `view.js`.

Нельзя заливать весь `configs/` поверх работающей конфигурации ради карты:
это может заменить адреса, политики и сохранённые настройки.
Обновление уже установленной карты или формы не требует пересборки PS;
если имена ссылок не менялись, достаточно заново открыть вкладку.

## Проверки без платы

```sh
./build.sh check
node tests/web/register-map.mjs
node tests/web/axp-register-map.mjs
BVSTK_PLAYWRIGHT_MODULE=/путь/к/playwright/index.mjs node tests/web/indicators.mjs
```

Браузерный тест использует локальные фикстуры, не подключается к плате
и проверяет обновление кэша, сохранение раскрытых секций, мобильную ширину,
отсутствие физических команд, отказоустойчивость и изоляцию JS.
