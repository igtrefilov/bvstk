# Формат профиля устройства v2

Профиль — JSON-файл с настройками одного оконечного устройства:
его адресом на шине, доступными регистрами, политикой доступа и параметрами
кэша. Например, для LAN8720 он задаёт адрес PHY и список опроса,
для AXP15060 — адрес I²C и разрешённые значения записи.

Документ состоит из двух частей:

- **Работа с текущей прошивкой:** полные примеры, справочник полей,
  настройка политики и сохранение.
- **Проектируемые расширения:** дополнительные протоколы и типы ресурсов.
  Их поддержка требует доработки PS; текущий загрузчик такие профили отклоняет.

## Что описывает профиль

Один профиль соответствует одному экземпляру устройства.
У двух одинаковых микросхем на разных адресах будут одинаковые
`device.model` и разные `id` и `transport.address`.

| Раздел | На какой вопрос отвечает |
|---|---|
| `device` | Что это за устройство? |
| `transport` | К какой шине и по какому адресу оно подключено? |
| `protocol` | Какой обработчик PS обслуживает обмен? |
| `defaults` | Какие свойства общие для всех регистров? |
| `resources` | Какие регистры доступны через профиль? |
| `policy` | Какие операции разрешены? |
| `settings` | Какие начальные значения кэша сохранены? |
| `observability` | Какие журналы обмена публикуются? |
| `register_map`, `view` | Как расшифровать и показать значения во вкладке «Показатели»? |

Платформа задаёт MMIO, IRQ, DMA и аппаратные ограничения контроллера.
Текущее состояние устройства — готовность `ready`, значения кэша, временные метки
и счётчики — доступно через API системы. Монтирование томов и
форматирование относятся к службе хранения.

## Поддержка в текущей прошивке

Загрузчик принимает два обработчика: `bvstk_i2c_bridge` и
`bvstk_mdio_bridge`. Они предоставляют регистровый доступ через
существующие PL-мосты.

| Сборка | I²C | MDIO |
|---|---|---|
| FreeRTOS | Загрузка v1 и v2, работа с устройством, сохранение v2 | Загрузка v1 и v2, работа с устройством, сохранение v2 |
| Нейтрино | Загрузка и сохранение через общий кодек | Общий кодек собирается; служба загрузки MDIO пока отсутствует |

Другие имена `protocol.driver` относятся к
[проектируемым расширениям](#проектируемые-расширения).

Основные ограничения действующих мостов:

| Параметр | I²C | MDIO |
|---|---|---|
| Контроллер | `pl_i2c_0` | `pl_mdio_0` |
| Адрес устройства | `0x00..0x7F`, 7 бит | `0x00..0x1F` |
| Число регистров | 1..256 | 1..32 |
| Адреса регистров | Все адреса от 0 до количества регистров минус 1 | То же |
| Размер значения | 8 бит | 16 бит |
| Доступ ресурса | `rw` | `rw` |
| Кэш и проверка записи | Режим `driver` | Режим `driver` |
| Политика чтения | Все чтения разрешены | Все чтения разрешены |
| Политика записи | Совпадение адреса и полного значения | Совпадение адреса и значения по маске |
| Правил в каждом списке записи | До 256 | До 64 |

`access: "rw"` описывает операции, доступные мосту. Физические свойства
регистра определяются документацией микросхемы: в этом диапазоне могут
быть регистры только для чтения и зарезервированные адреса. Выбирать
регистры для записи и опроса нужно с учётом этих свойств.

Мосты требуют непрерывный диапазон адресов. Для расшифровки физических
регистров используется отдельная карта `register_map.json`.
Поддержка разреженных ресурсов, RO, W1C и других эффектов в самом
профиле предусмотрена в проектируемой части спецификации.

## Файлы одного устройства

Каждое устройство хранится в отдельной папке:

```text
flash:/config/
├── i2c/
│   └── axp15060/
│       ├── axp15060.json       профиль
│       ├── register_map.json  описание физических регистров
│       └── view.js            компоновка вкладки «Показатели»
└── mdio/
    └── lan8720/
        ├── lan8720.json
        ├── register_map.json
        └── view.js
```

В репозитории такая же структура находится в `configs/`.
Рекомендуется одинаковое имя для `id`, папки и основного JSON-файла.

| Файл | Назначение | Обязателен |
|---|---|---|
| `<id>.json` | Адрес, обработчик, регистры, политика и настройки | Да |
| `register_map.json` | Названия битов, состояния и правила расшифровки | Нет |
| `view.js` | Индивидуальная форма показателей устройства | Нет |

Связь с дополнительными файлами задаётся в корне профиля:

```json
{
  "register_map": "register_map.json",
  "view": "view.js"
}
```

Это фрагмент корневого объекта. Оба имени относятся к папке устройства.
Формат карты и формы описан в [пакете устройства](device-bundles.md).

Браузер читает карту и форму для отображения кэша. Отсутствие этих файлов
оставляет основной обмен с устройством работоспособным. Карта и форма
устанавливаются во Flash отдельно от ELF.

## Полные примеры рабочих профилей

Ниже приведены два полных профиля для текущей прошивки.
Все регистры перечислены; каждый JSON-блок можно сохранить отдельным
файлом без дополнений. Примеры соответствуют штатным профилям репозитория.

При использовании на другом стенде проверьте адрес устройства,
список опроса и политику записи. Карты и формы должны лежать рядом
с профилем для работы вкладки «Показатели».

### LAN8720A на MDIO

В этом профиле:

- PHY находится по адресу `0x01` на `pl_mdio_0`.
- Представлены 32 регистра, от `0x00` до `0x1F`.
- Автоопрос обходит восемь регистров в указанном порядке.
- Между циклами опроса выдерживается пауза 50 мс.

  `0x00`, `0x04`, `0x12`, `0x1E`. Остальные записи запрещены.

а `0x14` проходит только проверку диапазона и запрещается политикой.

## Как подготовить профиль

1. Возьмите полный пример для нужной шины.
2. Задайте уникальный `id` и описание `device`.
3. Укажите контроллер и адрес в `transport`.
4. Перечислите непрерывный диапазон регистров, начиная с нуля.
   Общие параметры оставьте в `defaults.register`.
5. Настройте политику. Пустой whitelist записи блокирует все записи.
   Добавляйте разрешения по документации устройства и требованиям стенда.
6. Для MDIO выберите регистры автоопроса. Учитывайте эффекты чтения:
   некоторые регистры при чтении очищают накопленные признаки.
7. При необходимости добавьте карту и форму показателей.
8. Проверьте JSON и совместимость с загрузчиком, затем разместите
   пакет в `flash:/config/<шина>/<id>/`.

Существующие системные профили загружаются при старте.
Изменения через shell и web UI относятся к рабочей конфигурации в RAM;
для сохранения используется команда `save`.

## Справочник полей текущей прошивки

В таблицах «по умолчанию» означает значение при отсутствии поля.
Обязательные свойства ресурса можно задать непосредственно в
`resources` или унаследовать из `defaults.register`.

### Типы значений

| Обозначение | Как записывать | Ограничение |
|---|---|---|
| `ID` | `"lan8720"`, `"reg_1f"` | 1..31 символ; шаблон `^[a-z][a-z0-9_-]{0,30}$` |
| `Text(N)` | `"LAN8720A"` | Непустой UTF-8, до N байт после декодирования JSON, без управляющих символов |
| `UInt(a..b)` | `50` | Целое JSON-число от a до b, только десятичные цифры; без знака, дроби и экспоненты |
| `Bool` | `true` или `false` | Логическое значение JSON |
| `Hex` | `"0x36"`, `"0xFFFF"` | Строка: `0x` и 1..16 шестнадцатеричных цифр; максимум `0xFFFFFFFFFFFFFFFF` |
| `Duration` | `1000` | Миллисекунды, целое число от 0 до 600000; смысл нуля зависит от поля |
| `Bytes` | `"0xA001"` | Строка из полных пар hex-цифр после `0x`; используется в проектируемых расширениях |

Адреса, значения и маски записываются строками `Hex`.
Количество битов и интервалы записываются числами:

```json
{
  "address": "0x01",
  "width_bits": 16,
  "autopoll_cycle_delay_ms": 50
}
```

Этот фрагмент показывает типы значений; поля относятся к разным
разделам профиля. У `Hex` допустимы ведущие нули и буквы обоих регистров.
При сохранении используется запись вида `"0x00FF"`.
Ширину регистра задаёт `width_bits`.

### Общие ограничения

| Что проверяется | Предел |
|---|---|
| Размер документа | 65536 байт UTF-8, без BOM |
| Вложенность JSON | До 16 уровней контейнеров; корневой объект — первый |
| Число ресурсов | I²C: 1..256; MDIO: 1..32 |
| Правил в каждом списке записи | I²C: 0..256; MDIO: 0..64 |
| Элементов `cache_seed` | I²C: 0..256; MDIO: 0..32 |
| Таблица ID ресурсов | До 2048 байт, включая завершающий ноль каждой строки и один служебный байт |

JSON должен содержать уникальные ключи. Комментарии, завершающие запятые,
`null`, неизвестные поля и неверная кодировка вызывают отказ загрузки.
Имена полей и значения перечислений чувствительны к регистру.

Ошибка любого поля отклоняет весь профиль. Это относится и к превышению
лимитов: массивы целиком проходят проверку до применения конфигурации.

### Корневой объект

| Поле | Назначение и тип | Обязательно | По умолчанию |
|---|---|---|---|
| `schema_version` | Версия формата, число `2` | Да | — |
| `id` | Уникальный среди загруженных профилей `ID` устройства | Да | — |
| `device` | Объект с описанием модели | Да | — |
| `transport` | Объект с параметрами подключения | Да | — |
| `protocol` | Объект с именем обработчика и его параметрами | Да | — |
| `resources` | Непустой массив регистров | Да | — |
| `defaults` | Общие свойства в объекте `register` | Нет | `{}` |
| `policy` | Объект политики; для мостов обязателен `read` | Да | — |
| `settings` | Сохранённые начальные значения кэша | Нет | Пустые списки, применение при старте выключено |
| `observability` | Публикация телеметрии и событий | Нет | Оба включены |
| `register_map` | Имя файла карты регистров | Нет | Карта отсутствует |
| `view` | Имя JS-формы; требует `register_map` | Нет | Стандартное отображение карты |

Для `register_map` допустимо `register_map.json` или имя с окончанием
`_register_map.json`. У формы расширение `.js`. Основа имени
состоит из ASCII-букв, цифр, `_` и `-`; всё имя занимает до 63 символов.
Указывайте только имя файла в папке устройства. Пути, URL и подкаталоги
загрузчик отклоняет.

Метаданные `device`, ID ресурсов, `register_map` и `view` сохраняются
при изменении конфигурации через интерфейсы системы. Карта и форма
управляют отображением; политика, опрос и кэш задаются основным профилем.

### Описание устройства

| Поле `device` | Назначение и тип | Обязательно | По умолчанию |
|---|---|---|---|
| `model` | Модель, `Text(64)` | Да | — |
| `vendor` | Производитель, `Text(64)` | Нет | Производитель не указан |
| `class` | Класс из таблицы ниже | Нет | `generic` |
| `label` | Подпись, `Text(96)` | Нет | Для отображения используется `id` |

| `class` | Назначение |
|---|---|
| `generic` | Устройство общего назначения |
| `phy` | Трансивер физического уровня сети |
| `power` | Управление питанием |
| `gpio` | Дискретные входы и выходы |
| `sensor` | Измерительное устройство |
| `memory` | Микросхема памяти |
| `storage` | Носитель данных |
| `bridge` | Преобразователь протоколов |
| `serial` | Оконечное устройство последовательного обмена |

Класс нужен для группировки устройств в интерфейсе.
Обработчик выбирается полем `protocol.driver`, готовность определяется
службой шины. В действующих интерфейсах сохраняются прежние имена
устройств и числовые адреса регистров; поддержка новых подписей зависит
от конкретного представления.

### Подключение к шине

| Поле `transport` | Назначение и тип | I²C | MDIO |
|---|---|---|---|
| `bus` | Обязательное имя шины | `"i2c"` | `"mdio"` |
| `controller` | Обязательный ID контроллера | `"pl_i2c_0"` | `"pl_mdio_0"` |
| `address` | Обязательный `Hex`, адрес устройства | `"0x00".. "0x7F"` | `"0x00".. "0x1F"` |
| `address_bits` | Разрядность адреса | Только `7`; по умолчанию `7` | Поле запрещено |

Адрес I²C задаётся без бита направления. Частота общей линии настраивается
на уровне контроллера. Допустимые адреса конкретной микросхемы могут
занимать часть диапазона формата.

Одна физическая цель описывается одним профилем. Для I²C её определяют
контроллер, разрядность и адрес; для MDIO — контроллер и адрес PHY.
Выбирайте уникальное подключение при добавлении устройства.

### Обработчик и параметры I²C

| Поле `protocol` | Назначение и тип | Обязательно | По умолчанию |
|---|---|---|---|
| `driver` | Строка `"bvstk_i2c_bridge"` | Да | — |
| `options` | Объект параметров | Да | — |

| Поле `protocol.options` | Назначение и тип | Обязательно | По умолчанию |
|---|---|---|---|
| `max_write_value` | `Hex`, наибольшее значение записи: `0x00..0x40` | Да | — |
| `capture_cache_on_save` | `Bool`, только `true`: сохранять действительные значения кэша | Нет | `true` |

При `max_write_value: "0x40"` общий допустимый диапазон записи —
от 0 до 64 включительно. Затем значение проверяется политикой.
Каждое правило I²C сравнивает весь байт: `match.mask` должен быть
`"0xFF"`, `match.value` — в пределах `max_write_value`.

Таймаут обмена определяет вызывающая операция. Поле
`protocol.timeout_ms` текущим обработчиком не поддерживается.

### Обработчик и параметры MDIO

| Поле `protocol` | Назначение и тип | Обязательно | По умолчанию |
|---|---|---|---|
| `driver` | Строка `"bvstk_mdio_bridge"` | Да | — |
| `options` | Объект параметров | Нет | `{}` |

| Поле `protocol.options` | Назначение и тип | Обязательно | По умолчанию |
|---|---|---|---|
| `autopoll_enabled` | `Bool`, включить обход списка опроса | Нет | `false` |
| `autopoll_order` | Массив до 32 уникальных ID существующих регистров, в порядке обхода | Нет | `[]` |
| `autopoll_reg_delay_ms` | Пауза между регистрами, `UInt(0..60000)`, мс | Нет | `0` |
| `autopoll_cycle_delay_ms` | Пауза между циклами, `UInt(0..600000)`, мс | Нет | `50` |

Опрос последовательно обходит список. Продолжительность цикла включает
обмен и обе разновидности пауз. Отключение `autopoll_enabled` сохраняет
список и интервалы. Проверка идентификаторов PHY службой обнаружения
продолжается независимо от автоопроса.

Таймаут обмена задаёт вызывающая операция; `protocol.timeout_ms`
в этом обработчике также не поддерживается.

### Регистры и общие свойства

Каждый регистр имеет собственные `id`, `kind` и `address`.
Политики, настройки и опрос ссылаются на его `id`.

| Поле ресурса | Назначение | Обязательно | Значения в текущей прошивке |
|---|---|---|---|
| `id` | Уникальный внутри профиля `ID` | Да, в ресурсе | Например, `"reg_13"` |
| `kind` | Тип ресурса | Да, в ресурсе | Только `"register"` |
| `address` | Адрес регистра на устройстве, `Hex` | Да, в ресурсе | I²C: `0x00..0xFF`; MDIO: `0x00..0x1F` |
| `width_bits` | Число битов значения | Да | I²C: `8`; MDIO: `16` |
| `access` | Доступные мосту операции | Да | `"rw"` |
| `write_mask` | Маска битов передаваемого слова | Да | I²C: `"0xFF"`; MDIO: `"0xFFFF"` |
| `cache` | Управление кэшем | Да | `{"mode": "driver"}` |
| `verify` | Проверка записи | Да | `{"mode": "driver"}` |

Адреса должны образовывать непрерывный диапазон от нуля. Порядок элементов
массива может отличаться от порядка адресов; повторы адресов и ID запрещены.
Удобно придерживаться имён `reg_00`, `reg_01` и далее.

Общие свойства можно вынести в `defaults.register`. Например:

```json
{
  "defaults": {
    "register": {
      "width_bits": 16,
      "access": "rw",
      "write_mask": "0xFFFF",
      "cache": {"mode": "driver"},
      "verify": {"mode": "driver"}
    }
  },
  "resources": [
    {"id": "reg_00", "kind": "register", "address": "0x00"}
  ]
}
```

Это фрагмент профиля. После наследования ресурс `reg_00` получает
все пять свойств из `defaults.register`. Явно заданное свойство ресурса
заменяет соответствующее общее свойство. Вложенные объекты и массивы
заменяются целиком. `defaults` действует на перечисленные ресурсы.

Следующие поля зарезервированы для расширенной семантики.
В текущих мостах они допускают только нейтральные значения:

| Поле | Допустимое значение при явном указании | При отсутствии |
|---|---|---|
| `read_effect` | Объект с нулевыми масками `clear_mask`, `latch_high_mask`, `latch_low_mask` | Все маски нулевые |
| `write_effect` | Объект с нулевыми `one_clear_mask`, `one_set_mask`, `self_clear_mask`, `fixed_mask`, `fixed_value` | Все значения нулевые |
| `refresh` | `{"on": [], "period_ms": 0}`; поля можно опускать | Фоновое обновление этого механизма выключено |
| `persist_mask` | Нулевая строка `Hex` | Ноль |
| `fields` | `[]` | Пустой список |

Автоопрос MDIO задаётся через `protocol.options.autopoll_*`.
Остальные режимы ресурсов описаны в проектируемых расширениях.

## Политики безопасности

Политика проверяет операции, проходящие через сервис PS.
Для текущих мостов доступны два раздела: `policy.read` и `policy.write`.

### Чтение

Оба моста требуют разрешить все чтения:

```json
{
  "read": {
    "mode": "blacklist",
    "rules": []
  }
}
```

Это содержимое `policy`. Часть внешних чтений обслуживается PL
самостоятельно, поэтому сервис PS поддерживает здесь только пустой
blacklist. Ограничивающая политика чтения вызывает отказ загрузки.

### Запись

| Поле `policy.write` | Назначение и тип | Обязательно | По умолчанию |
|---|---|---|---|
| `mode` | `"whitelist"` или `"blacklist"` | Да, если задан `write` | — |
| `rules` | Массив активных правил | Нет | `[]` |
| `inactive_rules` | Массив правил противоположного режима | Нет | `[]` |

Если весь раздел `write` отсутствует, записи запрещены.

| Режим | Правило совпало | Совпадений нет | Пустой список |
|---|---|---|---|
| `whitelist` | Разрешить | Запретить | Запретить все записи |
| `blacklist` | Запретить | Разрешить | Разрешить все допустимые записи |

Разрешение списка действует вместе с проверками адреса, диапазона
значения, состояния устройства и возможностей драйвера. Например,
I²C отклонит значение выше `max_write_value` при любой политике.

`rules` и `inactive_rules` проходят одинаковую проверку и оба
сохраняются. Команда `policy set whitelist|blacklist` меняет их роли.
При ручном редактировании JSON переносите списки вместе с изменением
режима: одна правка `mode` изменит смысл тех же правил.

### Правило и маска

| Поле правила | Назначение | Обязательно |
|---|---|---|
| `resource` | ID существующего регистра | Да |
| `match` | Условие сравнения записываемого значения | I²C: да; MDIO: можно опустить |
| `match.value` | Образец, `Hex` | Вместе с `mask` |
| `match.mask` | Биты, участвующие в сравнении, `Hex` | Вместе с `value` |

Условие совпадения:

```text
(записываемое_значение & mask) == (match.value & mask)
```

Оператор `&` оставляет только биты, отмеченные маской.

| Пример | Что совпадёт |
|---|---|
| I²C: `value="0x12"`, `mask="0xFF"` | Только полный байт `0x12` |
| MDIO: `value="0x0100"`, `mask="0xFFFF"` | Только полное слово `0x0100` |
| MDIO: `value="0x0100"`, `mask="0x0100"` | Любое слово с установленным битом 8 |
| MDIO: `value="0x0000"`, `mask="0x0000"` | Любое допустимое значение |

У I²C разрешена только маска `0xFF`.
У MDIO отсутствие `match` или `match: {}` означает любое допустимое
значение выбранного регистра. Если задано `value` или `mask`,
обязательна вся пара. Обе величины должны помещаться в ширину регистра.

Например, разрешение ровно одного значения регистра AXP15060:

```json
{
  "write": {
    "mode": "whitelist",
    "rules": [
      {
        "resource": "reg_13",
        "match": {"value": "0x12", "mask": "0xFF"}
      }
    ],
    "inactive_rules": []
  }
}
```

Это фрагмент `policy`; раздел `read` нужно сохранить.
Правило даёт разрешение на будущую запись. Применение самой политики
физической записи не выполняет.

Маски имеют разные задачи:

| Поле | Задача |
|---|---|
| `write_mask` | Определяет биты передаваемого слова; у текущих мостов охватывает всё слово |
| `match.mask` | Выбирает биты для сравнения в правиле политики |
| `max_write_value` | Ограничивает числовое значение записи I²C |
| `persist_mask` | В проектируемом обработчике определяет сохраняемые биты настройки |

### Границы контроля

Сервис PS проверяет собственные операции и обрабатываемые им входные
записи моста. Прямой привилегированный доступ через MMIO и JTAG находится
вне этого механизма.

MDIO slave самостоятельно отвечает на часть чтений внешнего мастера
из ведомого кэша. Каждое такое чтение PS не получает.
Контроль этих чтений и точное воспроизведение эффектов чтения требуют
аппаратной поддержки. Ограничения ядра приведены в
[описании MDIO](../development/drivers/mdio.md).

## Кэш и сохранение

### Что означает режим driver

В режиме `driver` кэшем и проверкой записи управляет служба шины:

| Шина | Поведение |
|---|---|
| I²C | Сохраняет прочитанные значения и значения разрешённых записей в рабочем кэше |
| MDIO | После записи читает результат и публикует прочитанное значение в BRAM; обработку сброса PHY выполняет служба MDIO |

Универсальное сравнение записи по маске и время годности кэша
в этих профилях пока отсутствуют. Их проектные режимы называются
`masked_readback` и `snapshot`.

### Сохранённые настройки

| Поле `settings` | Назначение и тип | Обязательно | Текущая прошивка |
|---|---|---|---|
| `cache_seed` | Массив начальных значений кэша | Нет | По умолчанию `[]` |
| `desired` | Желаемые физические настройки, проектируемая функция | Нет | Только `[]` |
| `apply_on_startup` | Применять физические настройки при старте | Нет | Только `false`, также по умолчанию |

Элемент `cache_seed` содержит два обязательных поля:

| Поле | Назначение |
|---|---|
| `resource` | ID существующего регистра |
| `value` | Начальное значение, `Hex`: I²C `0x00..0xFF`, MDIO `0x0000..0xFFFF` |

Каждый регистр встречается в списке один раз. Например:

```json
{
  "settings": {
    "cache_seed": [
      {"resource": "reg_13", "value": "0x12"}
    ],
    "desired": [],
    "apply_on_startup": false
  }
}
```

Этот фрагмент задаёт начальное значение кэша.
Источник такого значения — сохранённая конфигурация; физическое значение
и готовность устройства определяются после обмена. Загрузка
`cache_seed` оставляет физические регистры без изменений.

### Что делает save

Команды в shell bvstk:

```text
i2c axp15060 save
mdio lan8720 save
```

Последовательность сохранения:

1. Сервис берёт текущую конфигурацию из RAM.
2. Для I²C действительные значения рабочего кэша переносятся в
   `cache_seed`. Сохраняются и прочитанные байты выше `max_write_value`.
3. Конфигурация записывается в файл устройства.
4. В FreeRTOS предыдущий файл остаётся как `<id>.json.bak`.

`save` работает с уже имеющимися данными. Дополнительных чтений шины
и применения значений к физическому устройству эта команда не выполняет.
`desired` остаётся пустым.

При ошибке сохранения рабочая конфигурация RAM остаётся действующей.
Защита файла при потере питания зависит от файлового слоя. При незавершённой
замене и отсутствии основного файла FreeRTOS восстанавливает
`.json.bak` до обращения к встроенным значениям. Полное повреждение FAT
требует отдельного восстановления.

## Телеметрия и события

| Поле `observability` | Назначение | Обязательно | Текущая прошивка |
|---|---|---|---|
| `telemetry` | Публиковать доступные сервису наблюдения обмена | Нет | Только `true`, также по умолчанию |
| `events` | Публиковать попытки операций с побочными эффектами, отказы и результаты | Нет | Только `true`, также по умолчанию |

Телеметрия позволяет определить источник данных: внешний обмен,
опрос со стороны PS или работа с локальным кэшем. Результат операции
показывает, чем она завершилась. При ошибке чтения значение отсутствует;
предыдущие данные могут сохраняться с соответствующим статусом.

Эти поля отвечают за публикацию. Автоопрос и разрешения операций
настраиваются своими разделами. Обязательные системные сообщения об
ошибках сохраняются независимо от настроек журналов.

Объём журналов и доступные наблюдения зависят от реализации.
Программные потери и усечение данных должны обозначаться явно.
Потери на стороне PL можно учитывать только при наличии аппаратных данных.

## Проверка профиля

Перед установкой проверьте:

- версия равна `2`, ID и имена файлов корректны;
- выбран поддерживаемый контроллер и обработчик;
- адреса регистров идут от нуля без пропусков;
- все ссылки в политике, опросе и `cache_seed` ведут к существующим ID;
- ширина значений, маски и размеры списков укладываются в ограничения;
- используются допустимые для текущего обработчика режимы.

Проверка синтаксиса файла на Linux:

```sh
jq empty configs/mdio/lan8720/lan8720.json
```

`jq` проверяет синтаксис JSON. Проверки поддерживаемых полей,
ссылок, масок и аппаратных ограничений выполняются загрузчиком PS.
Машиночитаемая JSON Schema пока отсутствует.

Проверки проекта из корня репозитория:

```sh
./scripts/check_docs.sh
./build.sh check
```

Тесты профилей проверяют миграцию пяти штатных устройств,
решения политик по диапазонам значений, повторное сохранение обоих
списков правил, начальные значения кэша, порядок опроса и отказ на
ошибочных полях. Это проверки на компьютере.

| Причина отказа | Что проверить |
|---|---|
| Неизвестный обработчик | Для текущей PS выбрать `bvstk_i2c_bridge` или `bvstk_mdio_bridge` |
| Пропуск адреса ресурса | Перечислить весь диапазон от нуля |
| Недопустимая маска I²C | Использовать `match.mask: "0xFF"` |
| Запись I²C вне диапазона | Сопоставить `match.value` с `max_write_value` |
| Ссылка на неизвестный ресурс | Проверить совпадение `resource` и `resources[].id` |
| Неподдерживаемый режим | Проверить `cache`, `verify`, `refresh`, `desired`, `observability` |

Неверный профиль отклоняется целиком до применения.
При запуске повреждённый или неподдерживаемый файл останавливает
загрузку соответствующей шины. Это помогает сохранить заданные
ограничения доступа при ошибке конфигурации.

## Совместимость и переход с v1

PS читает старые файлы без `schema_version`.
При явном `save` они сохраняются в v2, если имя соответствует типу `ID`.
Файлы со старыми именами, содержащими, например, точку или заглавную
букву, сохраняются в прежнем формате с прежним именем.
Неизвестная версия вызывает отказ загрузки.

| Старое поле | Поле или поведение v2 |
|---|---|
| `name` | `id`, имя сохраняется |
| `addr_7b`, `phy_addr` | `transport.address` и указание шины |
| `reg_count` | Явный непрерывный набор `resources` |
| `max_value_code` | `protocol.options.max_write_value` для I²C |
| `autopoll_regs` и интервалы | `protocol.options.autopoll_*` для MDIO, с сохранением порядка |
| `policy`, `whitelist`, `blacklist` | `policy.write.mode`, `rules`, `inactive_rules` |
| `settings` | `settings.cache_seed` |
| Рабочий кэш I²C | Действительные значения включаются в `cache_seed` при `save` |
| Желаемые физические настройки | `desired: []`, `apply_on_startup: false` |

Повторяющиеся начальные значения одного регистра I²C при миграции
сводятся к последнему значению.

Обновление ELF сохраняет существующие файлы во Flash.
Порядок миграции: обновить PS, загрузить имеющиеся профили,
выполнить `save` для каждого устройства. Сам переход формата сохраняет
разрешения и порядок опроса.

HTTP-конфигурация сохраняет прежнее представление с полями `name`,
`reg_count`, `policy`, `settings` и другими. Обновление через HTTP
сохраняет метаданные v2. Форматы DCP2, телеметрии, событий и команд shell
совместимы с прежними интерфейсами.

Дополнительные сведения:
[конфигурация](configuration.md),
[поддержка сборками](profiles.md),
[пакет устройства](device-bundles.md).

### Общие правила расширенного формата

Корневые поля и описание `device` сохраняют типы из основного справочника.
Дополнительно предусмотрены следующие возможности:

| Поле | Проектируемое поведение |
|---|---|
| `transport.bus` | `i2c`, `mdio`, `spi`, `uart`, `sd` |
| `resources[].kind` | `register`, `command`, `stream`, `block` |
| `defaults` | Общие свойства каждого поддерживаемого типа ресурсов |
| `policy` | Необязателен; по умолчанию `{}`, все операции запрещены |
| `settings` | По умолчанию пустые списки, `apply_on_startup: false` |
| `observability.telemetry`, `observability.events` | `Bool`, по умолчанию `true`; также допускается `false` |

Общие пределы: 1..256 ресурсов, до 256 правил одной операции,
до 256 элементов каждого списка `settings`, до 64 битовых полей регистра.
Лимиты документа и вложенности остаются прежними. Конкретная сборка
может устанавливать меньшие пределы; превышение отклоняет весь профиль.

У `Hex` доступны значения до 64 бит. Проверка диапазона выполняется
до преобразования к типу C. Браузер должен использовать точную
целочисленную обработку для 64-битных значений.
`Bytes` хранит пары hex-цифр слева направо; `"0x"` означает
пустую последовательность.

### Подключение и обработчики расширений

`transport.bus` и `transport.controller: ID` обязательны.
Остальные поля зависят от шины. Поле от другой шины вызывает отказ.

#### I²C и MDIO

Для I²C предусмотрены `address: Hex` и `address_bits`:
`7` по умолчанию либо `10`. Диапазоны — `0x00..0x7F`
и `0x000..0x3FF` соответственно. Поддержку адресации и допустимость
зарезервированных адресов проверяет драйвер.

У MDIO остаётся обязательный `address: Hex`, `0x00..0x1F`.
Обработчик выбирает Clause 22 или Clause 45.

#### SPI

| Поле `transport` | Тип и допустимые значения | Обязательно | По умолчанию |
|---|---|---|---|
| `chip_select` | `UInt(0..255)`, существующий CS контроллера | Да | — |
| `mode` | `UInt(0..3)` | Нет | `0` |
| `max_hz` | `UInt(1..4294967295)`, верхний предел частоты | Да | — |
| `bits_per_word` | `8`, `16`, `32` | Нет | `8` |
| `bit_order` | `msb_first`, `lsb_first` | Нет | `msb_first` |

Контроллер выбирает поддерживаемую частоту до `max_hz` включительно.
Если подходящей частоты нет, профиль отклоняется.
`bit_order` задаёт порядок битов в слове. Порядок байтов регистра,
управление CS и границы транзакций определяет протокол.

#### UART

| Поле `transport` | Тип и допустимые значения | Обязательно | По умолчанию |
|---|---|---|---|
| `baud_rate` | `UInt(1..4294967295)`, поддерживаемая портом скорость | Да | — |
| `data_bits` | `5`, `6`, `7`, `8`, `9` | Нет | `8` |
| `parity` | `none`, `even`, `odd` | Нет | `none` |
| `stop_bits` | `1`, `2` | Нет | `1` |
| `flow_control` | `none`, `rts_cts` | Нет | `none` |

`uart_raw` занимает порт целиком. Для нескольких адресуемых участников
нужен обработчик прикладного протокола; его адреса задаются в
`protocol.options`. Общего `transport.address` для UART нет.

#### Нативная SD

| Поле `transport` | Тип и допустимые значения | Обязательно | По умолчанию |
|---|---|---|---|
| `slot` | `UInt(0..255)`, физический слот | Да | — |
| `max_hz` | `UInt(1..4294967295)`, предел частоты | Нет | По возможностям контроллера и карты |

Для нативного подключения используется `bus: "sd"`.
Для SD по SPI используется `bus: "spi"` с обработчиком `sd_spi`.

Одна физическая цель имеет одного владельца профиля.
Для SPI цель определяется контроллером и CS, для SD — контроллером
и слотом. Повторное описание цели другим профилем отклоняется.
Несовместимые настройки одного UART-порта также вызывают отказ.

#### Обработчики протокола

| Поле `protocol` | Тип и назначение | Обязательно | По умолчанию |
|---|---|---|---|
| `driver` | `ID` зарегистрированного обработчика | Да | — |
| `timeout_ms` | `Duration`, 1..600000 мс; предел низкоуровневой транзакции | Нет | `100` |
| `options` | Объект параметров обработчика | Нет | `{}` |

Проектируемые обработчики:

| `driver` | Шина | Ресурсы | Требования |
|---|---|---|---|
| `mdio_clause22` | MDIO | `register` | Адрес регистра `0x00..0x1F`, значение 16 бит, `options: {}` |
| `mdio_clause45` | MDIO | `register` | Адрес `0x0000..0xFFFF`, обязательный `mmd`, значение 16 бит, `options: {}` |
| `i2c_regmap` | I²C | `register` | Адрес и порядок байтов задаются параметрами ниже |
| `spi_raw` | SPI | `command` | Только `transfer`, 8-битные слова, `options: {}` |
| `uart_raw` | UART | `stream` | Поток байтов, `data_bits: 8`, `options: {}` |
| `sd_spi` | SPI | `block` | `mode: 0`, 8-битные слова, `msb_first`, `options: {}` |
| `sd_native` | SD | `block` | Согласование параметров контроллером, `options: {}` |

Неизвестный обработчик или параметр отклоняется. Расширение реестра
сохраняет смысл существующих полей; изменение их смысла требует
новой версии контракта.

Параметры `i2c_regmap`:

| Поле `options` | Допустимые значения | По умолчанию | Назначение |
|---|---|---|---|
| `register_address_bits` | `8`, `16` | `8` | Разрядность адреса регистра |
| `register_address_order` | `big`, `little` | `big` | Порядок байтов адреса |
| `value_byte_order` | `big`, `little` | `big` | Порядок байтов значения |
| `repeated_start` | `Bool` | `true` | Повторный START между адресом регистра и чтением |

Одна операция `i2c_regmap` работает с одним регистром.
Автоинкремент, переключение страниц и пакетные записи требуют
специализированного контракта.

В `spi_raw.transfer` каждый байт запроса создаёт восемь тактов
и один байт ответа. Запрос непустой, ответ имеет ту же длину;
`response.max_bytes >= request.max_bytes`. CS удерживается всю операцию.
Класс побочного эффекта — `opaque`: обработчик передаёт байты
с неизвестным для него смыслом.

### Ресурсы и наследование расширений

Каждый ресурс содержит собственные `id: ID` и `kind`.
ID уникален внутри профиля. Ссылки в настройках и правилах используют ID.

| `kind` | Что представляет | Значения `access` | Операции |
|---|---|---|---|
| `register` | Адресуемое числовое значение | `none`, `ro`, `wo`, `rw` | `read`, `write` |
| `command` | Запрос и ответ | `none`, `execute` | `execute` |
| `stream` | Поток байтов | `none`, `ro`, `wo`, `rw` | `read`, `transmit` |
| `block` | Диапазон блоков носителя | `none`, `ro`, `wo`, `rw` | `read`, `write`, при поддержке `erase` |

`none` запрещает операции, `ro` разрешает направление чтения,
`wo` — записи, `rw` — оба. Политика проверяется дополнительно.

Каждая физическая сущность описывается один раз. Дублирующий ресурс
отклоняется; у блоков проверяется также пересечение диапазонов.
Сочетание разных типов допустимо при явной поддержке обработчиком.

`defaults` содержит объекты `register`, `command`, `stream`,
`block`. Общими могут быть поля соответствующего типа, кроме
`id`, `kind`, `address`, `mmd`, `operation` и `first_block`.

Порядок получения свойств:

1. Взять `defaults.<kind>`.
2. Заменить свойства явно заданными полями ресурса.
3. Заполнить пропуски значениями по умолчанию из спецификации.
4. Проверить результат и взаимные ограничения.

Вложенные объекты и массивы заменяются целиком. Например,
`cache: {"mode": "none"}` полностью заменит унаследованный объект
`cache`, включая `max_age_ms`. Затем применяются собственные
умолчания нового объекта. Неизвестные поля запрещены и в `defaults`.
Доступны только явно перечисленные ресурсы.

### Регистры расширенного обработчика

#### Основные поля

| Поле | Тип и назначение | Обязательно | По умолчанию |
|---|---|---|---|
| `id` | `ID`, имя ресурса | Да | — |
| `kind` | Строка `"register"` | Да | — |
| `address` | `Hex`, адрес регистра устройства | Да | — |
| `mmd` | `Hex`, `0x00..0x1F` | Для Clause 45; у остальных перечисленных обработчиков запрещено | — |
| `width_bits` | `8`, `16`, `32`, `64` | Да, можно через `defaults` | — |
| `access` | `none`, `ro`, `wo`, `rw` | Нет | `none` |
| `write_mask` | `Hex`, биты для записи | Нет | Ноль |
| `read_effect` | Объект эффектов чтения | Нет | Все маски нулевые |
| `write_effect` | Объект эффектов записи | Нет | Все маски и фиксированное значение нулевые |
| `cache` | Объект режима кэша | Нет | `{"mode": "none"}` |
| `refresh` | Объект обновления | Нет | `{"on": [], "period_ms": 0}` |
| `verify` | Объект проверки записи | Нет | `{"mode": "none"}` |
| `persist_mask` | `Hex`, биты сохраняемой настройки | Нет | Ноль |
| `fields` | Массив описаний битовых полей | Нет | `[]` |

Значения и маски помещаются в `width_bits`.

| Доступ | Требования |
|---|---|
| `ro`, `none` | `write_mask`, `persist_mask` и маски эффектов записи равны нулю |
| `wo`, `rw` | Эффективная `write_mask` ненулевая |
| `wo` | Кэш чтения, фоновое чтение, проверка чтением и эффекты чтения запрещены; `persist_mask` равна нулю |

#### Эффекты чтения

`read_effect` — объект со следующими необязательными полями
типа `Hex`; по умолчанию все равны нулю:

| Поле | Поведение физического регистра |
|---|---|
| `clear_mask` | Указанные биты очищаются при чтении |
| `latch_high_mask` | Зафиксированная единица удерживается до чтения |
| `latch_low_mask` | Зафиксированный ноль удерживается до чтения |

Маски попарно не пересекаются. После чтения защёлкнутого состояния
значение определяется текущим условием устройства. В наблюдение
попадает результат физического чтения.

Ненулевая маска требует поддержки драйвером. Явное чтение обычным
мастером допустимо; фоновое чтение и публикация в ведомый кэш требуют
согласованного владельца события. Несовместимое сочетание с
`refresh`, кэшем или `verify` отклоняется. Чтение локального кэша
возвращает сохранённое наблюдение и само по себе физический эффект
регистра не воспроизводит.

#### Эффекты записи

Поля объекта `write_effect` имеют тип `Hex`,
необязательны и по умолчанию равны нулю:

| Поле | Поведение |
|---|---|
| `one_clear_mask` | Запись единицы очищает бит, W1C |
| `one_set_mask` | Запись единицы устанавливает бит, W1S |
| `self_clear_mask` | Устройство самостоятельно сбрасывает командный бит |
| `fixed_mask` | Биты с обязательным фиксированным значением при передаче |
| `fixed_value` | Требуемое значение битов `fixed_mask` |

Первые три маски попарно не пересекаются и входят в `write_mask`.
Остальные биты `write_mask` получают переданное значение обычным
присваиванием. `fixed_mask` и `write_mask` не пересекаются;
единицы `fixed_value` допускаются только внутри `fixed_mask`.

Перед записью проверяются условия:

```text
(value & fixed_mask) == fixed_value
(value & ~(write_mask | fixed_mask)) == 0
```

Инверсия ограничивается шириной регистра. Неверное слово отклоняется.
После проверки масок применяется политика.

Обычная запись передаёт проверенное слово целиком.
Сохранение неизвестных резервных битов, зависимые команды и
специальные последовательности требуют отдельного обработчика.

#### Режимы кэша

| `cache.mode` | Поведение | Дополнительные условия |
|---|---|---|
| `none` | Постоянный кэш чтения выключен; телеметрия операции доступна | Другие поля запрещены |
| `snapshot` | Последнее успешное чтение с источником, временем и признаком достоверности | `max_age_ms: Duration`, 1..600000, по умолчанию 1000 |
| `static` | Значение хранится до сброса, потери устройства, повторного обнаружения или замены профиля | Только `ro`, без эффектов чтения, `refresh.period_ms: 0`; другие поля запрещены |
| `driver` | Логика существующей службы I²C или MDIO | Только адаптеры `bvstk_*_bridge`; другие поля запрещены |

По истечении `max_age_ms` снимок считается устаревшим.
Чтение запускается отдельно настройками обновления или явной операцией.
Ошибка обмена сохраняет прежнее значение только со статусом старых данных.
Начальные значения `cache_seed` имеют отдельный источник.

Успешная передача записи и подтверждённое чтением состояние
учитываются раздельно. Для динамического статуса подходит `snapshot`;
`static` предназначен для стабильных данных.
Допустимы только перечисленные объектные режимы кэша.

#### Обновление кэша

| Поле `refresh` | Тип и значения | По умолчанию |
|---|---|---|
| `on` | Массив уникальных `startup`, `reconnect`, `write_complete` | `[]` |
| `period_ms` | `Duration`, целевой период; `0` выключает периодический опрос | `0` |

| Событие | Когда выполняется чтение |
|---|---|
| `startup` | После инициализации устройства |
| `reconnect` | После повторного обнаружения устройства |
| `write_complete` | После разрешённой и успешно переданной записи в ресурс |

Отказ политики или ошибка передачи завершают операцию без
`write_complete`. Чтение после записи также может завершиться ошибкой.
У ресурса без записи `write_complete` запрещён.

Активное обновление требует разрешённого чтения и включённого кэша.
Драйвер должен поддерживать выбранные события, в том числе обнаружение
переподключения для `reconnect`. Несовместимое требование отклоняется.

Фактический период зависит от занятости шины. Планировщик ограничивает
очередь пропущенных опросов; API сообщает возраст значения и ошибки.

#### Проверка записи

| Поле `verify` | Тип и назначение | По умолчанию |
|---|---|---|
| `mode` | `none`, `masked_readback`, `driver` | `none` |
| `mask` | `Hex`, ненулевая маска сравнения; обязательна для `masked_readback` | — |
| `timeout_ms` | `Duration`, 1..600000 мс | `100` |
| `delay_ms` | `Duration`, задержка первого чтения | `0` |
| `interval_ms` | `Duration`, 1..600000 мс, пауза повторных чтений | `1` |

Все поля, кроме `mode`, относятся только к `masked_readback`.
У `driver` используется проверка службы моста, у `none` проверка
выключена; дополнительные поля для этих режимов запрещены.

Для `masked_readback` нужны `access: "rw"`, безопасное физическое чтение
и разрешение политики на него. Маска включает только обычные биты
присваивания: командные, W1C, W1S, фиксированные и только читаемые биты
в неё не входят. Требуется `delay_ms < timeout_ms` и
`interval_ms <= timeout_ms`.

Проверка выполняется так:

1. Передать запись один раз.
2. Выдержать `delay_ms`.
3. Прочитать регистр и сравнить:
   `(read_value & mask) == (written_value & mask)`.
4. При несовпадении повторять безопасное чтение с паузой
   `interval_ms` до совпадения или истечения таймаута.

Ошибка обмена сразу завершает проверку. Таймаут измеряется монотонными
часами от окончания передачи записи. После срока новые чтения
не запускаются; ожидание ограничено оставшимся временем.
**Запись автоматически не повторяется.** При ошибке проверки
устройство уже могло изменить состояние.

Если включён `write_complete`, результат проверочного чтения
используется и для кэша. При `cache.mode: "none"` проверка работает
без постоянного хранения результата. Регистры с побочными эффектами
чтения требуют специализированного алгоритма.

#### Сохраняемые биты и подписи полей

`persist_mask` выбирает обычные биты присваивания для
`settings.desired`. Ноль запрещает включать регистр в этот список.
Желаемое значение задаётся отдельно; запись проходит обычную политику.

Элемент массива `fields`:

| Поле | Тип и назначение | Обязательно | По умолчанию |
|---|---|---|---|
| `id` | Уникальный ID поля внутри регистра | Да | — |
| `lsb` | `UInt(0..63)`, младший бит | Да | — |
| `width_bits` | `UInt(1..64)`, число битов | Да | — |
| `label` | `Text(96)`, подпись | Нет | `id` |
| `values` | Массив до 64 расшифровок | Нет | `[]` |

Требуется `lsb + width_bits` в пределах ширины регистра.
Поля не пересекаются. Элемент `values` содержит только
`value: Hex` и `label: Text(96)`. Код относится к извлечённому полю
после сдвига; коды уникальны и помещаются в его ширину.

Эти поля служат отображению. Доступ, маски и политика задаются
своими свойствами. Единицы измерения, масштабирование, формулы и
исполняемые выражения в `resources[].fields` этой редакцией
не предусмотрены.

### Командные ресурсы

| Поле | Тип и назначение | Обязательно | По умолчанию |
|---|---|---|---|
| `id` | `ID` ресурса | Да | — |
| `kind` | Строка `"command"` | Да | — |
| `operation` | `ID` операции выбранного обработчика | Да | — |
| `access` | `none`, `execute` | Нет | `none` |
| `effect` | `none`, `write`, `erase`, `reset`, `opaque` | Да | — |
| `request` | Объект описания запроса | Да | — |
| `response` | Объект описания ответа | Да | — |
| `timeout_ms` | `Duration`, 1..600000 мс; предел всей команды | Нет | `protocol.timeout_ms` |

В `request` и `response` обязательны
`encoding: "bytes"` и `max_bytes: UInt(0..4096)`.
Ноль допустим, когда операция поддерживает отсутствие данных.
Формат передаваемых байтов определяет спецификация обработчика.

`effect` должен соответствовать операции. Например,
`spi_raw.transfer` всегда имеет эффект `opaque`.
Любая команда проверяется по `policy.execute`.
Если команда и регистровая операция обращаются к одной физической цели,
обработчик обязан применить общие ограничения либо запретить такой
дублирующий доступ.

Командные ресурсы поддерживают только перечисленные свойства.
Автоматическое обновление, регистровый кэш, `verify`,
`persist_mask` и `settings` для них запрещены.
После таймаута действие уже могло состояться; автоматического повтора
нет. Пустой ответ сообщает об отсутствии данных ответа, подтверждение
результата определяется протоколом устройства.

### Потоковые ресурсы

| Поле | Тип и назначение | Обязательно | По умолчанию |
|---|---|---|---|
| `id` | `ID` ресурса | Да | — |
| `kind` | Строка `"stream"` | Да | — |
| `access` | `none`, `ro`, `wo`, `rw` | Нет | `none` |
| `encoding` | Строка `"bytes"` | Нет | `bytes` |
| `buffer_bytes` | `UInt(1..65536)`, на каждое разрешённое направление | Нет | `1024` |
| `max_chunk_bytes` | `UInt(1..4096)`, максимум данных одного вызова | Нет | `256` |
| `overflow` | `drop_oldest`, `drop_newest`, `pause` | Нет | `drop_newest` |

`ro` разрешает RX, `wo` — TX, `rw` — оба направления.
Для `none` буферы отсутствуют. `uart_raw` допускает один поток
на порт. Требуется `max_chunk_bytes <= buffer_bytes`.

| Режим переполнения RX | Действие |
|---|---|
| `drop_oldest` | Удалить самые старые данные |
| `drop_newest` | Отбросить поступившие данные |
| `pause` | Приостановить источник; требуется аппаратная или протокольная поддержка |

При отсутствии механизма приостановки `pause` отклоняется.
Для `wo` явное поле `overflow` запрещено.
Число программно отброшенных байтов учитывается отдельно от аппаратных
потерь, о которых сервису может быть неизвестно.

Заполненный TX возвращает ошибку или ожидает ограниченное время по
контракту обработчика. Частично выполненная передача отражается
в результате; автоматического повтора всей передачи нет.

Данные одного вызова API могут содержать часть сообщения или несколько
сообщений. Проверку структуры прикладного протокола выполняет
специализированный обработчик. Регистровые свойства и `settings`
для потока запрещены.

### Блочные ресурсы

| Поле | Тип и назначение | Обязательно | По умолчанию |
|---|---|---|---|
| `id` | `ID` ресурса | Да | — |
| `kind` | Строка `"block"` | Да | — |
| `access` | `none`, `ro`, `wo`, `rw` | Нет | `none` |
| `first_block` | `Hex`, начало на физическом носителе | Нет | `"0x00"` |
| `block_size_bytes` | `512`, `1024`, `2048`, `4096` | Да | — |
| `block_count` | Ненулевой `Hex` либо `"discover"` | Нет | `"discover"` |
| `erase_blocks` | `UInt(0..4294967295)`, размер группы стирания | Нет | `0`, стирание выключено |

При `discover` доступная длина определяется от `first_block`
до конца носителя. Драйвер проверяет размер блока и ёмкость после
обнаружения. Если ёмкость определить невозможно, ресурс остаётся
недоступным. Размер раздела файловой системы учитывается отдельно
от физической ёмкости карты.

Адреса запросов и правил отсчитываются от начала ресурса:

```text
физический_адрес = first_block + request_block
```

До обмена проверяются переполнение, положительная длина и весь
диапазон запроса.

Для стирания нужны записываемый ресурс, поддержка драйвера, ненулевой
`erase_blocks`, разрешение политики и выравнивание физического
диапазона по группе стирания.

Служба хранения отклоняет сырую запись и стирание тома, занятого
файловой системой. Форматирование выполняется отдельной операцией
службы хранения. Регистровый кэш, `refresh`, `verify`,
`persist_mask` и `settings` к содержимому носителя неприменимы.

### Политики расширенных операций

В `policy` предусмотрены `read`, `write`, `execute`,
`transmit`, `erase`. Отсутствующая операция запрещена.
Структура каждого раздела — `mode`, `rules`, `inactive_rules`,
как в [описании политики](#политики-безопасности).

Общие правила:

- Для whitelist достаточно одного совпавшего правила.
- Для blacklist любое совпадение запрещает операцию.
- Порядок правил значения не имеет.
- Ресурс, доступ, диапазон, маски, драйвер и состояние системы
  проверяются независимо от списка.
- Неописанный ресурс недоступен, в том числе при пустом blacklist.
- Правило может ссылаться только на подходящий для операции тип ресурса.
- Пустой список для неподдерживаемой операции допустим; выполнение
  этой операции остаётся недоступным.

Элемент правила содержит обязательный `resource: ID` и необязательный
`match: {}`. Ссылка указывает на один существующий ресурс;
шаблоны имён запрещены.

| Ресурс и операция | Поля `match` | Условие |
|---|---|---|
| Регистр, `read` | Только `{}` | Любое чтение ресурса |
| Регистр, `write` | Пара `value: Hex`, `mask: Hex` | Сравнение по маске |
| Команда, `execute` | `request_prefix: Bytes`, `max_bytes: UInt(0..4096)` | Все заданные условия выполняются одновременно |
| Поток, `read` и `transmit` | `max_bytes: UInt(1..4096)` | Размер одного запроса |
| Блок, `read`, `write`, `erase` | Пара `first_block: Hex`, `block_count: Hex` | Диапазон, длина больше нуля |

Если в паре задано одно поле, второе обязательно.
Пустой `match` охватывает весь ресурс.

Для регистра используется `(value & mask) == (rule_value & mask)`.
Нулевая маска совпадает с любым допустимым значением.
Значение и маска помещаются в ширину регистра.

Для команды префикс непустой и помещается в допустимый запрос.
`max_bytes` находится между длиной префикса и
`request.max_bytes`. Для потока он ограничен
`max_chunk_bytes`. Ограничение размера относится к одному вызову;
суммарная квота и частота вызовов этим полем не задаются.

Для блоков действуют особые правила диапазонов:

| Режим | Проверка диапазона |
|---|---|
| Whitelist | Одно правило должно целиком покрыть запрос |
| Blacklist | Любое пересечение с запрещённым диапазоном отклоняет весь запрос |

Соседние разрешённые диапазоны автоматически не объединяются.
Решение принимается для запроса целиком до начала обмена.

При чтении I²C передача адреса регистра входит в операцию `read`.
Служебные кадры блочного протокола входят в соответствующую операцию
над блоками. Состав обмена и инициализацию определяет обработчик.

Фоновое чтение, проверка записи, применение настроек, shell, HTTP
и DCP2 проходят одну политику. Проверка записи чтением требует
дополнительно разрешения чтения; при его отсутствии такая запись
отклоняется до начала.

[Границы контроля PL](#границы-контроля) сохраняются.
Если оборудование не позволяет обеспечить требование профиля,
загрузчик должен отклонить профиль.

### Желаемые настройки устройства

| Поле `settings` | Назначение | По умолчанию |
|---|---|---|
| `desired` | Явно заданные желаемые значения физических настроек | `[]` |
| `cache_seed` | Начальные значения кэша | `[]` |
| `apply_on_startup` | `Bool`, применять `desired` при старте | `false` |

Элемент `desired`:

| Поле | Тип и требования | Обязательно | По умолчанию |
|---|---|---|---|
| `resource` | ID регистра `rw` с ненулевой `persist_mask` | Да | — |
| `value` | `Hex`, единицы только внутри эффективной `mask` | Да | — |
| `mask` | `Hex`, ненулевое подмножество `persist_mask` | Нет | `persist_mask` |

Элемент `cache_seed` содержит только обязательные
`resource: ID` и `value: Hex`. Для него нужен читаемый регистр
с включённым кэшем и без эффектов чтения; значение помещается в ширину.

В каждом списке ресурс встречается один раз. Один регистр может
присутствовать в обоих списках: `desired` хранит целевую настройку,
`cache_seed` — начальное состояние кэша. Использование seed в ведомом
кэше требует поддержки драйвером и обозначения источника; несовместимое
сочетание отклоняется.

`desired` меняется отдельной операцией настройки.
Телеметрия, текущий статус и обычные физические записи автоматически
в него не переносятся. `persist_mask` задаёт сохраняемые биты;
их значения задаются в `desired`.

`save` сохраняет конфигурацию и явно заданные настройки.
Операции чтения шины и применения к устройству выполняются отдельно.
При ошибке сохранения RAM остаётся действующей; замена файла сохраняет
предыдущую пригодную версию в рамках гарантий файлового слоя.

При `apply_on_startup: true`:

1. Завершить инициализацию и проверки драйвера.
2. Применять настройки в порядке массива.
3. Для каждой записи проверить маски, политику и выполнить `verify`.
4. При первой ошибке остановиться и сообщить выполненную часть.

Физические изменения сохраняются; автоматического отката и повторного
применения нет.

Для частичной настройки обычные записываемые биты вне маски получают
безопасным физическим чтением. Драйвер должен сериализовать чтение
и запись. Командные биты остаются неактивными, фиксированные получают
`fixed_value`. Политика проверяет итоговое передаваемое слово.
При отсутствии безопасного механизма частичная настройка отклоняется.
Локальная сериализация PS действует только для его собственных операций;
независимый внешний мастер может обратиться к устройству между ними.

Команды, потоки и содержимое носителя в `settings` не сохраняются.
Имя сервисной команды явного применения будет определено при реализации
соответствующего обработчика.

### Проверка расширенного профиля

Статическая проверка выполняется до изменения активного профиля
и любого обмена:

1. Размер, кодировка, синтаксис JSON, уникальность ключей.
2. Версия, обязательные поля, типы, перечисления, допустимость ключей.
3. Наследование, диапазоны, уникальность ресурсов и правильность ссылок.
4. Согласованность масок, эффектов, доступа, кэша, обновления и проверки.
5. Поддержка контроллером и обработчиком.
6. Возможность фонового чтения, проверки записи, обнаружения
   переподключения и применения настроек.
7. Конфликты физических целей, владение ресурсами и доступная память.

Геометрия носителя, наличие и физическое состояние проверяются отдельным
этапом после обмена. Ошибка делает устройство недоступным с сохранением
требований безопасности.

При неудачной замене активный профиль остаётся прежним.
Если пригодного профиля ещё нет, устройство остаётся неактивным.
Проверка конфигурации выполняется без пробных записей и команд устройства.

Для диагностики предусмотрено сообщение с путём поля и причиной.
Пример рекомендуемого представления:

```text
resources[0].verify.mask: contains self-clearing bits
transport.address: exceeds the MDIO address range
protocol.driver: not supported by this firmware
policy.write.rules[0].resource: unknown resource
```

Это текстовый формат диагностики; числовые коды DCP2 определяются
отдельно. Проверка JSON Schema, когда она появится, будет дополняться
проверкой аппаратных возможностей и поведения конкретного устройства.

## Полные примеры проектируемых профилей

**Эти примеры требуют новых обработчиков. Текущая PS их отклоняет.**

Каждый пример ниже — самостоятельный полный JSON-документ.
Контроллеры и параметры должны соответствовать будущей реализации.
Физические записи, исполнение команд, передача UART и стирание
запрещены пустыми whitelist.

| Пример | Что показывает |
|---|---|
| [LAN8720A с описанием регистра](#lan8720a-с-описанием-регистра) | Маску записи, обновление кэша и проверку чтением |
| [PCA9536 с регистром входов](#pca9536-с-регистром-входов) | Читаемый регистр I²C и битовое поле |
| [Транзакция SPI](#транзакция-spi) | Командный ресурс с двоичным обменом |
| [Поток UART](#поток-uart) | Приём байтов, буфер и переполнение |
| [SD по SPI](#sd-по-spi) | Блочный ресурс с определением ёмкости |

### LAN8720A с описанием регистра

Здесь описан только `irq_mask` по адресу `0x1E`.
Другие регистры через этот профиль недоступны.
Маска `0x00FE` соответствует описанию Interrupt Mask Register в
[Microchip LAN8720A, раздел 4.2.13](https://ww1.microchip.com/downloads/en/DeviceDoc/00002165B.pdf).

Профиль разрешает чтение и настраивает обновление кэша.
Параметры `verify` задают способ проверки для случая, когда политика
в дальнейшем разрешит запись.

```json
{
  "schema_version": 2,
  "id": "lan8720",
  "device": {
    "vendor": "Microchip",
    "model": "LAN8720A",
    "class": "phy"
  },
  "transport": {
    "bus": "mdio",
    "controller": "pl_mdio_0",
    "address": "0x01"
  },
  "protocol": {
    "driver": "mdio_clause22",
    "timeout_ms": 100
  },
  "defaults": {
    "register": {
      "width_bits": 16,
      "access": "none",
      "cache": {"mode": "none"},
      "refresh": {
        "on": [],
        "period_ms": 0
      },
      "persist_mask": "0x0000"
    }
  },
  "resources": [
    {
      "id": "irq_mask",
      "kind": "register",
      "address": "0x1E",
      "access": "rw",
      "write_mask": "0x00FE",
      "read_effect": {},
      "write_effect": {},
      "cache": {
        "mode": "snapshot",
        "max_age_ms": 2000
      },
      "refresh": {
        "on": [
          "startup",
          "write_complete"
        ],
        "period_ms": 1000
      },
      "verify": {
        "mode": "masked_readback",
        "mask": "0x00FE",
        "timeout_ms": 100,
        "delay_ms": 0,
        "interval_ms": 1
      },
      "persist_mask": "0x00FE"
    }
  ],
  "policy": {
    "read": {
      "mode": "whitelist",
      "rules": [
        {
          "resource": "irq_mask"
        }
      ]
    },
    "write": {
      "mode": "whitelist",
      "rules": []
    }
  },
  "settings": {
    "desired": [],
    "cache_seed": [],
    "apply_on_startup": false
  },
  "observability": {
    "telemetry": true,
    "events": true
  }
}
```

Пример явной желаемой настройки для этого ресурса —
замена объекта `settings` следующим фрагментом:

```json
{
  "desired": [
    {"resource": "irq_mask", "value": "0x0000", "mask": "0x00FE"}
  ],
  "cache_seed": [],
  "apply_on_startup": false
}
```

Настройка задаёт целевое значение сохраняемых битов.
Для физического применения потребуются разрешение политики
и реализованная сервисная операция. Применение при старте выключено.

### SD по SPI

Ресурс `card` доступен для чтения.
Ёмкость определяется при инициализации; размер логического блока —
512 байт. Запись и стирание запрещены.

Этот пример и пример транзакции SPI используют один контроллер и CS.
Они показывают два самостоятельных варианта подключения и предназначены
для раздельного применения.

```json
{
  "schema_version": 2,
  "id": "sd_card",
  "device": {
    "model": "SD card",
    "class": "storage"
  },
  "transport": {
    "bus": "spi",
    "controller": "pl_spi_0",
    "chip_select": 0,
    "mode": 0,
    "max_hz": 400000,
    "bits_per_word": 8,
    "bit_order": "msb_first"
  },
  "protocol": {
    "driver": "sd_spi",
    "timeout_ms": 1000
  },
  "resources": [
    {
      "id": "card",
      "kind": "block",
      "access": "ro",
      "first_block": "0x00",
      "block_size_bytes": 512,
      "block_count": "discover",
      "erase_blocks": 0
    }
  ],
  "policy": {
    "read": {
      "mode": "whitelist",
      "rules": [
        {
          "resource": "card"
        }
      ]
    },
    "write": {
      "mode": "whitelist",
      "rules": []
    },
    "erase": {
      "mode": "whitelist",
      "rules": []
    }
  },
  "observability": {
    "telemetry": true,
    "events": true
  }
}
```

Для перехода рабочего устройства на любой из этих обработчиков
потребуются реализация в PS и проверка карты конкретной микросхемы.
В частности, `mdio_clause22` должен обеспечивать все объявленные эффекты,
режимы кэша и проверки записи; текущий `bvstk_mdio_bridge` сохраняет
описанное в начале документа поведение моста.
