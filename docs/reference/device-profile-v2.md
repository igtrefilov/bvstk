# Формат профиля устройства v2

Статус: спецификация с **реализованным подмножеством**, редакция 2
от 23 сентября 2026 года.

Штатные профили в `configs/i2c/` и `configs/mdio/` используют v2.
Каждый профиль находится в собственной папке `<id>/<id>.json`.
Рядом могут лежать карта регистров и JS-форма вкладки «Показатели»;
их формат описан в [пакете устройства](device-bundles.md).
Загрузчики принимают контракты `bvstk_i2c_bridge` и `bvstk_mdio_bridge`,
описанные в [разделе поддержки](#реализованное-подмножество).
Они сохраняют поведение существующих мостов. Остальные контракты этого
документа пока проектные: неизвестная или неподдерживаемая функция
отклоняется, а не игнорируется. PL не меняется.

Общие примеры в `docs/reference/examples/device-profile-v2/` показывают
проектируемые возможности, **не предназначены для загрузки текущей PS**
и не входят во встроенный набор. Рабочие примеры находятся в `configs/`.
Старый формат остаётся читаемым; совместимость и хранение описаны также
в [справочнике конфигурации](configuration.md).

## Назначение и границы

Профиль описывает один экземпляр оконечного устройства. Например, две
одинаковые микросхемы на разных адресах имеют одинаковую модель, но разные
`id` и `transport`. Контроллер шины, его MMIO, IRQ, DMA и аппаратные лимиты
задаются платформой, а не профилем оконечного устройства.

Разделы независимы по назначению:

- `device` описывает микросхему или устройство;
- `transport` определяет физическое подключение;
- `protocol` выбирает реализованный обработчик обмена;
- `resources` описывает доступные данные и операции;
- `policy` ограничивает операции сервиса;
- `settings` хранит явно заданные значения;
- `observability` управляет публикацией наблюдений.

Общий формат не является универсальным исполняемым драйвером. Нестандартная
адресация, последовательности команд, контрольные суммы и зависимости между
регистрами должны поддерживаться выбранным обработчиком. Нельзя объявлять
сложный регистр обычным только потому, что его особенности не выражены
общими полями. JSON не содержит скриптов, имён исполняемых файлов, MMIO
адресов или путей для динамической загрузки кода.

Состояние `ready`, измеренные значения, действительность кэша, временные
метки и счётчики находятся в runtime API, а не в профиле. Файловая система,
точка монтирования и форматирование относятся к службе хранения, а не
к карте ресурсов SD-карты.

## Реализованное подмножество

| Сборка | Контракт | Состояние |
|---|---|---|
| FreeRTOS | `bvstk_i2c_bridge` | Загрузка v1 и v2, работа I²C, сохранение v2 |
| FreeRTOS | `bvstk_mdio_bridge` | Загрузка v1 и v2, работа MDIO, сохранение v2 |
| Нейтрино | `bvstk_i2c_bridge` | Общий кодек v1 и v2, загрузка и сохранение I²C |
| Нейтрино | `bvstk_mdio_bridge` | Общий кодек собирается, служба загрузки MDIO не подключена |
| Все сборки | Остальные `driver` из общей спецификации | Не реализованы; профиль отклоняется |

Это адаптеры существующего регистрового моста, а не новые драйверы
семантики микросхем. Ресурс `reg_13` означает доступный мосту адрес
`0x13`; `access=rw` описывает возможность сырой операции моста,
**не подтверждает записываемость физического регистра**. Разрешённые
записи ограничивает прежняя политика. Зарезервированные адреса остаются
в прежнем диапазоне, но миграция не добавляет ни разрешений, ни опросов.
Для полноценного описания битовых полей, RO, W1C, очистки при чтении
или специальных последовательностей нужен отдельный реализованный
семантический обработчик. Одной правкой JSON он не появляется.

### Обязательные параметры адаптеров

| Поле | I²C | MDIO |
|---|---|---|
| `transport.bus` | `i2c` | `mdio` |
| `transport.controller` | Только `pl_i2c_0` | Только `pl_mdio_0` |
| `transport.address` | `0x00..0x7F` | `0x00..0x1F` |
| `transport.address_bits` | `7`, можно опустить | Поле запрещено |
| `protocol.driver` | `bvstk_i2c_bridge` | `bvstk_mdio_bridge` |
| `resources` | 1..256 регистров | 1..32 регистра |
| Адреса ресурсов | Без повторов и пропусков, от нуля до числа ресурсов минус один | То же |
| `width_bits` | `8` | `16` |
| `access` | Только `rw` | Только `rw` |
| `write_mask` | `"0xFF"` | `"0xFFFF"` |
| `cache` | Только `{"mode":"driver"}` | То же |
| `verify` | Только `{"mode":"driver"}` | То же |
| `policy.read` | Обязательно `{"mode":"blacklist","rules":[]}` | То же |
| `policy.write` | До 256 правил в каждом из двух списков | До 64 правил в каждом из двух списков |
| `settings.cache_seed` | До 256 различных ресурсов, значения `0x00..0xFF` | До 32 различных ресурсов, значения `0x0000..0xFFFF` |

`width_bits`, `access`, `write_mask`, `cache`, `verify` задаются
на ресурсе или в `defaults.register`. ID ресурсов произвольны по общему
шаблону; общая таблица их строк, включая завершающие нули и один служебный
байт, не больше 2048 байт. Метаданные `device` и ID сохраняются при
редактировании политик через shell и web UI. Интерфейсы пока отображают
прежние имена и числовые адреса, а не новые подписи ресурсов.

Допускаются только пустые `fields`, нулевой `persist_mask`, нулевые
маски эффектов, пустой `refresh.on` и `refresh.period_ms=0`; эти поля
можно опустить. `settings.desired` должен быть пустым,
`apply_on_startup=false`. У `observability` допустимы только
`telemetry=true` и `events=true`, в том числе по умолчанию.
`protocol.timeout_ms` не поддерживается: таймаут по-прежнему определяет
вызывающая операция. Другие режимы и неизвестные поля отклоняются целиком.

`driver` означает, что кэш и проверка записи остаются в ведении
существующего сервиса, без новой универсальной семантики. I²C сохраняет
свой кэш прочитанных и разрешённых записанных значений. MDIO сохраняет
чтение после записи, публикацию прочитанного результата в BRAM и прежнюю
обработку сброса PHY. Этот режим **не обещает** побитовую проверку
`masked_readback`, срок годности `snapshot` или моделирование всех
побочных эффектов физического регистра.

Политика чтения ограничена явным разрешением чтений: существующий PL
самостоятельно обслуживает часть ведомого пути. Поэтому вместо ложного
обещания запретить такие чтения любой ограничивающий `policy.read`
отклоняется. Записи по-прежнему проверяются сервисом PS.

### Параметры I²C

`protocol.options`:

| Поле | Допустимые значения | Умолчание |
|---|---|---|
| `max_write_value` | Обязательный `Hex`, `0x00..0x40` | Нет |
| `capture_cache_on_save` | Только `true` | `true` |

`max_write_value` — прежний числовой предел записи, не битовая маска.
Например, `0x40` разрешает диапазон 0..64 до проверки политики,
а не только бит 6. Каждое правило записи обязано иметь
`match.value` в этом диапазоне и `match.mask="0xFF"`; wildcard
и частичные маски I²C не реализованы.

Синхронизация настроек I²C сохраняет действительные значения рабочего
кэша в `cache_seed`, как ранее в `settings`, включая прочитанные байты
выше `max_write_value`. Команда `i2c <sel> save` выполняет эту
синхронизацию перед сохранением. Загрузка seed не записывает регистры
физического устройства. `desired` при этом не заполняется.

### Параметры MDIO

`protocol.options`:

| Поле | Допустимые значения | Умолчание |
|---|---|---|
| `autopoll_enabled` | `Bool` | `false` |
| `autopoll_order` | До 32 различных ID существующих ресурсов | `[]` |
| `autopoll_reg_delay_ms` | `UInt(0..60000)` | `0` |
| `autopoll_cycle_delay_ms` | `UInt(0..600000)` | `50` |

Список сохраняет прежний порядок, межрегистровую и межцикловую задержку;
это не преобразование в независимые таймеры `refresh.period_ms`.
При `autopoll_enabled=false` список и интервалы также сохраняются.
Штатная проверка идентификаторов PHY остаётся включённой, как прежде.
`match.mask=0` по-прежнему разрешает любое значение выбранного регистра.
`cache_seed` не является командой записи PHY или признаком готовности.

### Файлы, сохранение и совместимость

Встроенные рабочие профили:
[AXP15060](../../configs/i2c/axp15060/axp15060.json),
[PCA9536](../../configs/i2c/pca9536/pca9536.json),
[LAN8720A](../../configs/mdio/lan8720/lan8720.json),
[DP83848C](../../configs/mdio/dp83848c/dp83848c.json),
[KSZ8081RNA](../../configs/mdio/ksz8081rna/ksz8081rna.json).

Новая PS читает старые файлы без `schema_version`. При явном `save`
они записываются в v2, если имя подходит под `ID`. Старые имена,
например с точкой или заглавными буквами, не переименовываются молча:
такой файл сохраняется в прежнем формате. Неизвестная `schema_version`
никогда не обрабатывается как старый профиль.

Сохранённые файлы во Flash не заменяются встроенным набором при обновлении
ELF. Для миграции существующих настроек сначала обновляют PS, затем
выполняют `save` для каждого устройства. У FreeRTOS предыдущий файл
остаётся в `.json.bak`; если основной файл пропал при незавершённой
замене, backup восстанавливается до загрузки встроенных значений.
Повреждённый или неподдерживаемый файл отключает загрузку соответствующей
шины, а не подменяется разрешающим профилем по умолчанию. Полное
повреждение FAT не покрывается этой процедурой.

Оба списка записи сохраняются: `rules` — активный, `inactive_rules` —
противоположный. Переключение `policy set whitelist|blacklist` меняет
их роли, не стирая содержимое. Повторяющиеся старые seed I²C сводятся
к последнему значению регистра, как при прежней загрузке кэша.

HTTP-конфигурация остаётся совместимой проекцией со старыми полями
`name`, `reg_count`, `policy`, `settings` и т. д. PUT этой проекции
не теряет метаданные v2. DCP2, телеметрия, события и команды shell
не меняют формата из-за изменения файла.

Регрессионная проверка: `./build.sh check`. В неё входят сравнение
всех пяти профилей с неизменёнными v1-образцами, полные диапазоны
решений политик, round-trip обоих списков, seed и порядка опроса,
а также отказ на неверных и неподдерживаемых полях.

## Типы и общие ограничения

| Обозначение | Допустимые значения |
|---|---|
| `ID` | Строка по шаблону `^[a-z][a-z0-9_-]{0,30}$`, от 1 до 31 символа |
| `Text(N)` | Непустая строка UTF-8 длиной до N байт после декодирования JSON, без управляющих символов |
| `UInt(a..b)` | JSON-число с десятичными цифрами, целое в диапазоне a..b; без знака, дроби и экспоненты |
| `Bool` | Только JSON `true` или `false`, не строки и не числа |
| `Hex` | Строка по шаблону `^0x[0-9A-Fa-f]{1,16}$`; без знака и пробелов, значение от 0 до `0xFFFFFFFFFFFFFFFF` |
| `Bytes` | Строка `0x`, за которой следуют полные пары hex-цифр; порядок байтов слева направо; пустая последовательность — `0x` |
| `Duration` | `UInt(0..600000)`, миллисекунды; допустимость нуля уточняется для поля |

Адреса, значения регистров, маски и большие номера блоков задаются `Hex`.
Разрядности, индексы CS, размеры буферов и интервалы — JSON-числа.
`0x20` без кавычек не является допустимым JSON-числом. Десятичное `32`
не заменяет строку `"0x20"` в поле типа `Hex`.

При сохранении hex-цифры записываются в верхнем регистре с префиксом `0x`.
Ведущие нули допустимы; число цифр не определяет разрядность регистра.
Значения и маски проверяются до сужения к типу C. Для 64-битных полей
в браузере требуется точная целочисленная обработка, без преобразования
через неточное JSON-число или 32-битные побитовые операции JavaScript.

Общие форматные пределы этой редакции:

| Объект | Предел |
|---|---|
| Документ | 65536 байт UTF-8, без BOM |
| Вложенность JSON | 16 уровней контейнеров, корневой объект — первый |
| Ресурсы | От 1 до 256 |
| Правила одной операции | От 0 до 256 |
| Элементы каждого списка `settings` | От 0 до 256 |
| Битовые поля одного регистра | От 0 до 64 |

Драйвер и сборка вправе иметь меньшие лимиты. Превышение любого лимита
отклоняет весь профиль; усечение массива или отключение части его функций
не допускается. Эти пределы не означают, что существующие загрузчики
выделяют соответствующий объём памяти.

Неизвестные ключи, повторяющиеся ключи, неверный UTF-8, комментарии,
завершающие запятые и `null` запрещены. Перечисления чувствительны к регистру.
Отсутствующее необязательное поле получает документированное значение
по умолчанию. Неверное значение не заменяется умолчанием.

## Корневой объект

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `schema_version` | `UInt(2..2)` | Да | Только `2` |
| `id` | `ID` | Да | Уникальное имя экземпляра среди всех загруженных профилей |
| `device` | Объект | Да | Описание модели и класса |
| `transport` | Объект | Да | Подключение к зарегистрированному контроллеру |
| `protocol` | Объект | Да | Обработчик протокола |
| `resources` | Массив объектов | Да | Типизированные ресурсы, непустой массив |
| `defaults` | Объект | Нет | `{}`, общие свойства ресурсов по типам |
| `policy` | Объект | Нет | `{}`, все операции запрещены |
| `settings` | Объект | Нет | Пустые списки, без применения при старте |
| `observability` | Объект | Нет | `telemetry=true`, `events=true` |
| `register_map` | Строка | Нет | Имя карты рядом с профилем: `register_map.json` или `<имя>_register_map.json`, до 63 ASCII-символов; без пути |
| `view` | Строка | Нет | Имя JS-формы рядом с профилем, например `view.js`; до 63 ASCII-символов; требует `register_map` |

`register_map` и `view` поддерживаются текущими кодеками I²C и MDIO и
сохраняются при `apply` и `save`. Это метаданные визуализации: они не
меняют политику, опрос, кэширование и драйвер. Отсутствие файлов карты
или формы не отключает подсистему. Чтение и проверку этих файлов
выполняет браузер, а не обработчик шины в PS.

В v2 нет корневых `addr_7b`, `phy_addr`, `reg_count`, `max_value_code`,
`autopoll_*`, `whitelist`, `blacklist` и `default_register_class`.
Разреженная карта задаётся явно через `resources`, а не сплошным диапазоном.

## Описание устройства

| Поле `device` | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `model` | `Text(64)` | Да | Модель, например `LAN8720A` |
| `vendor` | `Text(64)` | Нет | Не указан; отображается как неизвестный |
| `class` | Перечисление | Нет | `generic` |
| `label` | `Text(96)` | Нет | Для отображения используется `id` |

Допустимые `class`: `generic`, `phy`, `power`, `gpio`, `sensor`, `memory`,
`storage`, `bridge`, `serial`. Это группировка для интерфейса, а не выбор
драйвера, разрешение доступа или признак готовности. Класс описывает
оконечное устройство, а не шину.

| Класс | Назначение |
|---|---|
| `generic` | Устройство без более узкой классификации |
| `phy` | Трансивер физического уровня сети |
| `power` | Управление питанием |
| `gpio` | Управление дискретными входами и выходами |
| `sensor` | Измерительное устройство |
| `memory` | Микросхема памяти |
| `storage` | Носитель данных, представленный как хранилище |
| `bridge` | Преобразователь протоколов |
| `serial` | Оконечное устройство последовательного обмена |

## Подключение к шине

Общие обязательные поля `transport`:

| Поле | Тип | Допустимые значения |
|---|---|---|
| `bus` | Перечисление | `i2c`, `mdio`, `spi`, `uart`, `sd` |
| `controller` | `ID` | Идентификатор контроллера из реестра платформы |

`pl_i2c_0` и `pl_mdio_0` — реализованные идентификаторы адаптеров
мостов. Имена остальных контроллеров в примерах пока проектные. Параметры ниже допустимы только для указанной
шины. Например, `chip_select` в объекте `mdio` является ошибкой.

Одна физическая цель имеет одного владельца профиля: для I²C это контроллер,
разрядность адреса и адрес; для MDIO — контроллер и адрес PHY; для SPI —
контроллер и CS; для нативной SD — контроллер и слот. `uart_raw` целиком
владеет портом. Повторное описание той же цели другим профилем отклоняется,
даже если `id` отличается. Поддержка нескольких адресуемых участников UART
должна быть определена отдельным обработчиком прикладного протокола.

### I²C

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `address` | `Hex` | Да | Адрес без бита направления |
| `address_bits` | Перечисление чисел | Нет | `7`; также допускается `10` |

Для 7 бит диапазон `0x00..0x7F`, для 10 бит — `0x000..0x3FF`.
Допустимость конкретного адреса и зарезервированных адресных режимов
дополнительно проверяет драйвер. Объявление 10-битного адреса не добавляет
его поддержку существующему PL. Частота общей линии относится к настройке
контроллера, а не отдельного профиля.

### MDIO

| Поле | Тип | Обязательно | Значение |
|---|---|---|---|
| `address` | `Hex` | Да | Адрес PHY, `0x00..0x1F` |

Clause 22 или Clause 45 выбирается через `protocol.driver`. Поля с названием
`addr_7b` нет. Допустимые физические адреса конкретной микросхемы могут быть
уже диапазона формата.

### SPI

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `chip_select` | `UInt(0..255)` | Да | Индекс CS в контроллере |
| `mode` | `UInt(0..3)` | Нет | `0` |
| `max_hz` | `UInt(1..4294967295)` | Да | Верхний предел частоты обмена |
| `bits_per_word` | Перечисление чисел | Нет | `8`; также `16`, `32` |
| `bit_order` | Перечисление | Нет | `msb_first`; также `lsb_first` |

Контроллер выбирает поддерживаемую частоту не выше `max_hz`. Если это
невозможно, профиль отклоняется. Поле `bit_order` не задаёт порядок байтов
многобайтного регистра. Управление CS и допустимые границы транзакций
определяет протокол. Допускается только реально существующий CS.

### UART

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `baud_rate` | `UInt(1..4294967295)` | Да | Требуемая скорость, которую должен поддерживать порт |
| `data_bits` | Перечисление чисел | Нет | `8`; также `5`, `6`, `7`, `9` |
| `parity` | Перечисление | Нет | `none`; также `even`, `odd` |
| `stop_bits` | Перечисление чисел | Нет | `1`; также `2` |
| `flow_control` | Перечисление | Нет | `none`; также `rts_cts` |

Адреса участника прикладного протокола относятся к `protocol.options`,
если выбранный обработчик их определяет. Общего поля `address` для UART
нет. Две несовместимые настройки одного порта не могут применяться вместе.

### Нативная SD

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `slot` | `UInt(0..255)` | Да | Индекс физического слота контроллера |
| `max_hz` | `UInt(1..4294967295)` | Нет | Предел задаётся контроллером и согласованием с картой |

`bus=sd` означает нативный SD-контроллер. Для карты с обменом по SPI
используются `bus=spi` и обработчик `sd_spi`. Это разные варианты
подключения одного типа блочного устройства.

## Протокол устройства

| Поле `protocol` | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `driver` | `ID` | Да | Зарегистрированный обработчик из таблицы ниже |
| `timeout_ms` | `Duration`, не ноль | Нет | `100`, предел одной низкоуровневой транзакции |
| `options` | Объект | Нет | `{}`, поля определяются обработчиком |

Начальный набор контрактов v2:

| `driver` | `bus` | Ресурсы | Ограничения и `options` |
|---|---|---|---|
| `mdio_clause22` | `mdio` | `register` | Адрес регистра `0x00..0x1F`, значение 16 бит, `options={}` |
| `mdio_clause45` | `mdio` | `register` | Адрес регистра `0x0000..0xFFFF`, обязательный `mmd`, значение 16 бит, `options={}` |
| `i2c_regmap` | `i2c` | `register` | Параметры адреса и порядка байтов ниже |
| `spi_raw` | `spi` | `command` | Только операция `transfer`, 8-битные слова, `options={}` |
| `uart_raw` | `uart` | `stream` | Поток байтов, `data_bits=8`, `options={}` |
| `sd_spi` | `spi` | `block` | `mode=0`, 8-битные слова, `msb_first`, `options={}` |
| `sd_native` | `sd` | `block` | Параметры обмена согласует контроллер, `options={}` |

Таблица определяет проектируемые имена и контракты, **не список уже
подключённых драйверов**. Новая модель устройства может потребовать нового
обработчика и отдельного описания его `options` и операций. Неизвестный
обработчик или неизвестный параметр отклоняется. Само имя не является
путём к библиотеке. Дополнение реестра не разрешает менять смысл уже
описанных полей без изменения версии контракта.

Поля `options` для `i2c_regmap`:

| Поле | Тип | Умолчание | Смысл |
|---|---|---|---|
| `register_address_bits` | `8` или `16` | `8` | Разрядность адреса регистра в транзакции |
| `register_address_order` | `big` или `little` | `big` | Порядок байтов адреса |
| `value_byte_order` | `big` или `little` | `big` | Порядок байтов значения |
| `repeated_start` | `Bool` | `true` | Повторный START между передачей адреса регистра и чтением |

Общий обработчик выполняет одну операцию над одним регистром. Он не
предполагает автоинкремент, переключение страниц или безопасность пакетной
записи соседних регистров. Такие возможности требуют отдельного контракта.

Для `spi_raw.transfer` каждый байт запроса создаёт восемь тактов и один
байт ответа. Длина ответа равна длине запроса, `response.max_bytes` должна
быть не меньше `request.max_bytes`. Запрос непустой. CS удерживается
в течение всей операции. Данные не трактуются как регистры или безопасные
команды чтения; эффект операции считается `opaque`.

## Ресурсы и наследование

Каждый элемент `resources` имеет обязательные `id: ID` и `kind`.
Идентификаторы ресурсов уникальны внутри профиля. Политики и настройки
ссылаются на `id`, а не на номер элемента массива.

| `kind` | Назначение | Допустимый `access` | Операции |
|---|---|---|---|
| `register` | Адресуемое числовое значение | `none`, `ro`, `wo`, `rw` | `read`, `write` |
| `command` | Запрос и ответ по протоколу | `none`, `execute` | `execute` |
| `stream` | Поток байтов | `none`, `ro`, `wo`, `rw` | `read` для RX, `transmit` для TX |
| `block` | Массив блоков | `none`, `ro`, `wo`, `rw` | `read`, `write`; при поддержке — `erase` |

`none` запрещает операции, `ro` допускает только чтение, `wo` — только
запись или передачу, `rw` — оба направления. Во всех случаях дополнительно
проверяется политика. Два дескриптора одной физической сущности внутри
профиля запрещены: нельзя обходить политику через второй `id`. Для блоков
проверяется также пересечение диапазонов. Несколько типов ресурсов допустимы
только у обработчика, который явно поддерживает их сочетание.

`defaults` может содержать ключи `register`, `command`, `stream`, `block`.
Каждый задаёт свойства соответствующего типа из его таблиц ниже, кроме
`id`, `kind`, `address`, `mmd`, `operation` и `first_block`. Неизвестные
свойства запрещены и в `defaults`.

Порядок получения эффективного ресурса:

1. Взять поля `defaults.<kind>`.
2. Заменить их явно заданными полями ресурса.
3. Заполнить оставшиеся пропуски умолчаниями данной спецификации.
4. Проверить обязательные поля, типы и все взаимные ограничения.

Вложенный объект заменяется целиком, а не сливается рекурсивно. Например,
`cache: {"mode":"none"}` удаляет унаследованный `max_age_ms`.
Массивы также заменяются целиком. После замены к новому объекту применяются
его собственные документированные умолчания.

`defaults` действует только на перечисленные ресурсы. Он не создаёт
регистры для пропущенных адресов и не разрешает доступ к неизвестным данным.

## Регистры

### Основные поля

| Поле           | Тип                      | Обязательно                   | Значение или умолчание                               |
| -------------- | ------------------------ | ----------------------------- | ---------------------------------------------------- |
| `id`           | `ID`                     | Да                            | Имя ресурса                                          |
| `kind`         | Строка                   | Да                            | `register`                                           |
| `address`      | `Hex`                    | Да                            | Адрес в пространстве выбранного обработчика, не MMIO |
| `mmd`          | `Hex`, `0x00..0x1F`      | Для Clause 45                 | В остальных начальных обработчиках запрещено         |
| `width_bits`   | `8`, `16`, `32` или `64` | Да, возможно через `defaults` | Разрядность значения                                 |
| `access`       | Перечисление             | Нет                           | `none`                                               |
| `write_mask`   | `Hex`                    | Нет                           | Ноль, биты, которые разрешено задавать при записи    |
| `read_effect`  | Объект                   | Нет                           | Все маски равны нулю                                 |
| `write_effect` | Объект                   | Нет                           | Все маски и фиксированное значение равны нулю        |
| `cache`        | Объект                   | Нет                           | `{"mode":"none"}`                                    |
| `refresh`      | Объект                   | Нет                           | `{"on":[],"period_ms":0}`                            |
| `verify`       | Объект                   | Нет                           | `{"mode":"none"}`                                    |
| `persist_mask` | `Hex`                    | Нет                           | Ноль, сохранение значения регистра запрещено         |
| `fields`       | Массив объектов          | Нет                           | `[]`, расшифровка битовых полей                      |

Все значения и маски помещаются в `width_bits`. Для `ro` и `none`
`write_mask`, `persist_mask` и маски эффектов записи должны быть нулевыми.
Для `wo` и `rw` обязательна ненулевая эффективная `write_mask`.
Для `wo` запрещены кэш значений чтения, фоновое чтение, проверка чтением
и маски эффектов чтения. `persist_mask` для `wo` в этой редакции равна нулю:
универсальный механизм безопасного частичного восстановления не задан.

### Эффекты чтения

`read_effect` — объект, а не строка `none`. Все поля имеют тип `Hex`
и по умолчанию равны нулю:

| Поле | Смысл |
|---|---|
| `clear_mask` | Биты, очищаемые физическим чтением |
| `latch_high_mask` | Биты, удерживающие зарегистрированную единицу до чтения |
| `latch_low_mask` | Биты, удерживающие зарегистрированный ноль до чтения |

Маски попарно не пересекаются. Защёлкивание не означает безусловного
обнуления: после чтения поведение определяется текущим условием устройства.
Результат физического чтения записывается как наблюдение, а не заменяется
программно ожидаемым значением после очистки.

Ненулевая маска требует поддержки побочного эффекта драйвером. Для обычного
мастера допустимо явно читать такой регистр, но фоновое чтение и публикация
в ведомый кэш требуют согласованного владельца события. Без этой поддержки
сочетание с `refresh`, кэшем или `verify` отклоняется. Нельзя считать,
что локальное чтение кэша равнозначно чтению физического регистра.

### Эффекты записи

`write_effect` — объект. Все поля имеют тип `Hex`, умолчание — ноль:

| Поле | Смысл |
|---|---|
| `one_clear_mask` | Запись единицы очищает соответствующий бит |
| `one_set_mask` | Запись единицы устанавливает соответствующий бит |
| `self_clear_mask` | Командные биты, самостоятельно сбрасываемые устройством |
| `fixed_mask` | Биты, которые должны иметь фиксированное значение в отправляемом слове |
| `fixed_value` | Требуемые значения битов `fixed_mask` |

Первые три маски попарно не пересекаются и являются подмножествами
`write_mask`. Остальные биты `write_mask` имеют обычную семантику
присваивания. `fixed_mask` не пересекается с `write_mask`;
`fixed_value` не содержит единиц вне `fixed_mask`.

При записи проверяются все условия:

```text
(value & fixed_mask) == fixed_value
(value & ~(write_mask | fixed_mask)) == 0
```

Инверсия ограничивается разрядностью регистра. Неверное слово отклоняется,
а не молча маскируется. Эти проверки не заменяют политику. Обычная запись
не выполняет неявное чтение и изменение отдельных битов. Если устройству
нужно сохранять неизвестные резервные биты, выполнять последовательность
или учитывать взаимозависимость команд, требуется специализированный
обработчик; одних масок недостаточно.

### Кэш

| Поле `cache` | Тип | Значение или умолчание |
|---|---|---|
| `mode` | `none`, `snapshot`, `static`, `driver` | `none`; адаптеры мостов требуют явного `driver` |
| `max_age_ms` | `Duration`, не ноль | Только для `snapshot`, по умолчанию `1000` |

- `driver`: только для `bvstk_i2c_bridge` и `bvstk_mdio_bridge`;
  применяется существующая логика сервиса, другие поля кэша запрещены.
- `none`: значение не хранится как доступный для чтения кэш; телеметрия
  отдельной операции при этом возможна. `max_age_ms` запрещено.
- `snapshot`: последнее успешно прочитанное значение с источником,
  временем и признаком достоверности. После `max_age_ms` оно устарело.
- `static`: значение сохраняется до сброса, потери устройства, повторного
  обнаружения или замены профиля. Допустимо только при `access=ro`,
  отсутствии эффектов чтения и `refresh.period_ms=0`.
  `max_age_ms` запрещено. Не подходит для динамического статуса.

Истечение срока не является самостоятельной командой чтения. На ошибке
обмена прежнее значение нельзя выдавать как свежее. Оно может оставаться
в истории с соответствующим статусом. Значение из `cache_seed` имеет
отдельный источник и не подтверждает наличие устройства.

Режимы `mirror`, `immutable` и строка `cache="none"` не входят в v2.
Успешное завершение передачи записи не означает, что записанное слово
можно объявить подтверждённым содержимым физического регистра.

### Обновление

| Поле `refresh` | Тип | Значение или умолчание |
|---|---|---|
| `on` | Массив уникальных строк | `[]`; разрешены `startup`, `reconnect`, `write_complete` |
| `period_ms` | `Duration` | `0` — периодический опрос отключён; `1..600000` — целевой период |

`startup` выполняет чтение после инициализации устройства, `reconnect` —
после его повторного обнаружения. `write_complete` выполняет чтение после
разрешённой и завершённой передачи записи этому ресурсу. Отказ политики
и неуспешная передача его не запускают. Само чтение всё равно может вернуть
ошибку. Для ресурса без записи `write_complete` недопустим.

Ненулевой период или непустой `on` требуют разрешённого чтения и
`cache.mode` не `none`. Планировщик не создаёт неограниченную очередь
пропущенных опросов. Период — целевой, а не гарантия точного времени
при занятой шине. В runtime должны быть видны возраст значения и ошибка.

В этой редакции нет неопределённого `event_or_periodic`: источник события
должен быть доступен драйверу. Если обнаружение отключения не поддерживается,
нельзя обещать `reconnect`; несовместимое требование отклоняется.

### Проверка записи

| Поле `verify` | Тип | Значение или умолчание |
|---|---|---|
| `mode` | `none`, `masked_readback` или `driver` | `none`; адаптеры мостов требуют явного `driver` |
| `mask` | `Hex` | Обязательно для `masked_readback`, ненулевая маска сравнения |
| `timeout_ms` | `Duration`, не ноль | Для `masked_readback`, по умолчанию `100` |
| `delay_ms` | `Duration` | Для `masked_readback`, по умолчанию `0`, задержка первого чтения |
| `interval_ms` | `Duration`, не ноль | Для `masked_readback`, по умолчанию `1`, минимальная пауза повторных чтений |

При `mode=driver` работает прежняя проверка сервиса моста; другие поля
запрещены, общее сравнение по маске не обещается.
При `mode=none` другие поля запрещены. Для `masked_readback` нужен `rw`,
безопасное физическое чтение и разрешение политики на него. Маска сравнения
должна быть подмножеством обычных битов присваивания: в неё не входят
командные биты, W1C, W1S, фиксированные и только читаемые биты.
`delay_ms < timeout_ms`, `interval_ms <= timeout_ms`.

Сравнение: `(read_value & mask) == (written_value & mask)`. После задержки
возможно повторение безопасных чтений до совпадения или истечения срока.
Ошибка обмена немедленно завершает проверку. Тайм-аут отсчитывается
монотонными часами от окончания передачи записи; новые чтения после
дедлайна не запускаются, ожидание ограничивается остатком времени.
**Физическая запись автоматически не повторяется.** Ошибка проверки
не означает отсутствия побочного эффекта записи.

Если одновременно включён `write_complete`, чтение проверки используется
для кэша без второго независимого чтения. При `cache=none` проверка
возможна без постоянного сохранения значения. Нельзя проверять регистр
с побочными эффектами повторным чтением по этому общему алгоритму.

### Сохранение и битовые поля

`persist_mask` — подмножество обычных битов присваивания. Ноль запрещает
включать регистр в `settings.desired`. Ненулевая маска не включает
автосохранение, не разрешает запись и не создаёт желаемое значение.

Элемент `fields`:

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `id` | `ID` | Да | Уникальное имя поля в регистре |
| `lsb` | `UInt(0..63)` | Да | Младший бит |
| `width_bits` | `UInt(1..64)` | Да | Ширина; `lsb + width_bits` не больше ширины регистра |
| `label` | `Text(96)` | Нет | Используется `id` |
| `values` | Массив объектов | Нет | `[]`, до 64 расшифровок |

Элемент `values` содержит только `value: Hex` и `label: Text(96)`.
Значение относится к извлечённому полю после сдвига, а не ко всему слову.
Значения уникальны и помещаются в ширину поля. Поля не пересекаются.
Они служат отображению, не меняют доступ, маски, политику или масштаб
физической величины. Единицы, формулы и исполняемые выражения этой
редакцией не определены и как произвольные ключи не принимаются.

## Команды

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `id` | `ID` | Да | Имя ресурса |
| `kind` | Строка | Да | `command` |
| `operation` | `ID` | Да | Операция, реализованная выбранным обработчиком |
| `access` | `none` или `execute` | Нет | `none` |
| `effect` | `none`, `write`, `erase`, `reset`, `opaque` | Да | Объявленный обработчиком класс побочного эффекта |
| `request` | Объект | Да | Формат и предел запроса |
| `response` | Объект | Да | Формат и предел ответа |
| `timeout_ms` | `Duration`, не ноль | Нет | `protocol.timeout_ms`, предел всей команды |

`request` и `response` содержат обязательные `encoding="bytes"` и
`max_bytes: UInt(0..4096)`. Другие кодировки в общем контракте не заданы.
Ноль допускается только если операция поддерживает отсутствие данных.
Формат содержимого байтов задаёт спецификация обработчика; JSON не
описывает произвольную грамматику сообщений.

`effect` нельзя выбирать вопреки обработчику: `spi_raw.transfer` всегда
`opaque`. Любая команда проверяется по политике `execute`, даже если
она внутри выполняет запись или чтение. Это не обход политики регистра:
обработчик обязан запрещать дублирующие способы доступа либо явно
декларировать их и применять ограничения к общей физической цели.

Команды не поддерживают автоматический `refresh`, регистровый кэш,
`verify`, `persist_mask` или `settings`. Тайм-аут не запускает повторную
команду и не гарантирует отмену уже выполненного действия. Нулевой ответ
не означает подтверждения применения команды устройством.

## Потоки

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `id` | `ID` | Да | Имя ресурса |
| `kind` | Строка | Да | `stream` |
| `access` | `none`, `ro`, `wo`, `rw` | Нет | `none` |
| `encoding` | Строка | Нет | Только `bytes` |
| `buffer_bytes` | `UInt(1..65536)` | Нет | `1024` на каждое разрешённое направление |
| `max_chunk_bytes` | `UInt(1..4096)` | Нет | `256`, не больше `buffer_bytes` |
| `overflow` | `drop_oldest`, `drop_newest`, `pause` | Нет | `drop_newest` |

`access` задаёт направление: RX для `ro`, TX для `wo`, оба для `rw`.
Для `none` буферы не создаются. `uart_raw` допускает один поток на порт.
`drop_oldest` и `drop_newest` определяют действие при переполнении RX;
число отброшенных программой байтов учитывается отдельно от неизвестных
аппаратных потерь. `pause` требует реального механизма приостановки
источника и отклоняется без такой возможности. Для `wo` явное поле
`overflow` запрещено, поскольку приёмного буфера нет.

При заполнении TX данные не отбрасываются молча: операция возвращает
ошибку или ограниченно ждёт по контракту обработчика. Если часть данных
уже отправлена, это отражается в результате. Повтор всей передачи
автоматически не выполняется.

Чанк API не является пакетом прикладного протокола. Для проверки структуры
сообщений нужен отдельный обработчик, а не фильтр отдельных чанков.
Регистровые свойства и `settings` для потока запрещены.

## Блочные устройства

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `id` | `ID` | Да | Имя ресурса |
| `kind` | Строка | Да | `block` |
| `access` | `none`, `ro`, `wo`, `rw` | Нет | `none` |
| `first_block` | `Hex` | Нет | `0x00`, начало ресурса на физическом носителе |
| `block_size_bytes` | `512`, `1024`, `2048` или `4096` | Да | Ожидаемый логический размер блока |
| `block_count` | `Hex` или строка `discover` | Нет | `discover`, доступная ёмкость от `first_block` до конца носителя |
| `erase_blocks` | `UInt(0..4294967295)` | Нет | `0` — стирание не предоставляется; иначе размер группы стирания |

Фиксированный `block_count` должен быть ненулевым. Значения не меняют
геометрию носителя: размер блока и вместимость проверяются при обнаружении.
Если драйвер не может определить ёмкость, `discover` не превращается
в неограниченный диапазон: ресурс остаётся недоступным. Конфигурационный
предел или размер раздела файловой системы не доказывает ёмкость карты.

Адреса запросов и правил политики отсчитываются от начала ресурса.
Физический адрес равен `first_block + request_block`. Проверяются
переполнение, положительная длина запроса и полный диапазон до I/O.
Для `erase` нужны записываемый ресурс, поддержка драйвера, ненулевое
`erase_blocks`, разрешение политики и выравнивание физического диапазона
по группе стирания.

Политика профиля не отменяет владение носителем файловой системой.
Сырые записи и стирание занятого тома должны отклоняться службой хранения.
Регистровый кэш, `refresh`, `verify`, `persist_mask` и `settings` не
применяются к содержимому носителя. Форматирование профилем не запускается.

## Политики безопасности

`policy` содержит только необязательные ключи `read`, `write`, `execute`,
`transmit`, `erase`. Отсутствующая операция запрещена. Значение каждого
ключа — объект:

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `mode` | `whitelist` или `blacklist` | Да | Режим проверки |
| `rules` | Массив объектов | Нет | `[]`, активный список |
| `inactive_rules` | Массив объектов | Нет | `[]`, сохранённый список противоположного режима |

В `whitelist` операция разрешена, если совпало хотя бы одно правило;
пустой список запрещает всё. В `blacklist` совпадение запрещает операцию;
пустой список не запрещает её дополнительно. В обоих режимах сохраняются
проверки ресурса, доступа, диапазонов, масок, драйвера и состояния системы.
Неописанный ресурс запрещён и при пустом blacklist. Порядок правил
не влияет на результат: это не список действий с приоритетами.

Правило не может ссылаться на ресурс неподходящего типа, например
`policy.write` на команду. Пустой список для не предоставляемой устройством
операции допустим: он не создаёт такую возможность. При чтении I²C
передача адреса регистра является частью операции `read`, а не отдельной
записью значения. Аналогично служебные кадры блочного протокола проверяются
в составе операции над блоками. Их безопасный состав и инициализация
устройства относятся к контракту обработчика.

Список `rules` относится к выбранному режиму, `inactive_rules` —
к противоположному и сейчас не участвует в принятии решений.
Оба проходят одинаковую проверку и сохраняются. При переключении режима
через интерфейс их содержимое меняется местами: прежний активный список
становится неактивным. Правка только `mode` вручную без обмена списков
инвертирует смысл прежних правил.

Элемент правила:

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `resource` | `ID` | Да | Существующий ресурс этого профиля, без wildcard |
| `match` | Объект | Нет | `{}`, любая допустимая операция над указанным ресурсом |

Допустимые поля `match` зависят от операции и типа:

| Тип и операция | Допустимые поля | Смысл |
|---|---|---|
| `register`, `read` | Только `{}` | Нельзя принимать решение о физическом чтении по ещё неизвестному результату |
| `register`, `write` | `value: Hex`, `mask: Hex` | Обязательная пара, если задано хотя бы одно поле |
| `command`, `execute` | `request_prefix: Bytes`, `max_bytes: UInt(0..4096)` | Префикс и верхняя граница размера запроса; условия объединены И |
| `stream`, `read` и `transmit` | `max_bytes: UInt(1..4096)` | Верхняя граница одного запрошенного чанка |
| `block`, `read`, `write`, `erase` | `first_block: Hex`, `block_count: Hex` | Обязательная пара диапазона, длина ненулевая |

У регистров проверяется `(value & mask) == (rule_value & mask)`.
`mask=0` совпадает с любым допустимым значением. Обе величины должны
помещаться в ширину регистра. Они не являются `write_mask`: маска
сопоставления политики и маска допустимых битов имеют разный смысл.

У команды префикс непустой, укладывается в предел запроса; `max_bytes`
не превышает `request.max_bytes` и не меньше длины префикса. У потока
предел не больше `max_chunk_bytes`. Эти поля не задают суммарную квоту
или ограничение скорости. Ограничение отдельного вызова не защищает
от нескольких последовательных вызовов.

У блоков whitelist требует, чтобы **одно правило целиком покрывало
запрос**. Несколько соседних правил автоматически не объединяются.
Для blacklist достаточно любого пересечения с запрещённым диапазоном;
отклоняется весь запрос до начала операции. `match={}` означает весь
ресурс. Нельзя делить запрос и выполнять только разрешённую часть.

Для фонового чтения, проверки записи и применения настроек действуют
те же политики, что для shell, HTTP и DCP2. Возможность передать кадр
не заменяет разрешение выполнить операцию. Проверка записи требует
дополнительно разрешённого чтения; при его отсутствии запись с таким
режимом не начинается.

### Область действия и ограничения PL

Политика применяется к операциям, проходящим через сервис PS, включая
обрабатываемые им входные записи моста. Это **не обещание контроля каждого
кадра на физических выводах**. Прямой привилегированный MMIO, JTAG и чтения,
которые PL обслуживает самостоятельно, не становятся подконтрольными PS
из-за появления поля `policy.read`.

Существующий MDIO slave не сообщает PS каждое чтение внешним мастером
ведомого кэша. Поэтому точная семантика очистки после внешнего чтения
и отдельные ограничения таких чтений требуют аппаратной поддержки.
Профиль с требованием, которое нельзя обеспечить, должен быть отклонён,
а не принят в ослабленном режиме. Сведения об ограничениях действующего
ядра приведены в [описании MDIO](../development/drivers/mdio.md).

## Настройки и сохранение

| Поле `settings` | Тип | Значение или умолчание |
|---|---|---|
| `desired` | Массив объектов | `[]`, явно заданные желаемые настройки |
| `cache_seed` | Массив объектов | `[]`, начальные значения кэша |
| `apply_on_startup` | `Bool` | `false`, не выполнять физические записи при старте |

Элемент `desired`:

| Поле | Тип | Обязательно | Значение или умолчание |
|---|---|---|---|
| `resource` | `ID` | Да | Регистр `rw` с ненулевой `persist_mask` |
| `value` | `Hex` | Да | Значение сохраняемых битов; единицы вне эффективной `mask` запрещены |
| `mask` | `Hex` | Нет | `persist_mask` ресурса; ненулевое подмножество этой маски |

Элемент `cache_seed` содержит только обязательные `resource: ID` и
`value: Hex`. Нужен читаемый регистр с включённым кэшем, без эффектов
чтения. Значение помещается в его разрядность. В каждом списке ресурс
встречается не более одного раза. Один ресурс может находиться в обоих
списках: их назначения различны.

`cache_seed` не отправляется устройству и не является подтверждённым
физическим значением. Он не доказывает готовность. Если драйвер допускает
его использование в ведомом кэше, источник остаётся явно обозначенным.
Иначе профиль с такой комбинацией отклоняется.

`desired` не заполняется автоматически из телеметрии, командных битов
или статуса. Обычная физическая запись также не меняет желаемую настройку
неявно. Для изменения `desired` требуется отдельная операция настройки.
`persist_mask` разрешает сохранение битов, но не задаёт их значения.

`save` сохраняет текущую конфигурацию и явно заданные настройки в файл.
Он не читает шину для снимка всех регистров, не применяет настройки
к устройству и не копирует весь рабочий кэш в `desired`. Состояние RAM
не откатывается при ошибке сохранения; файл заменяется с сохранением
предыдущей пригодной версии. Конкретная гарантия при потере питания
определяется файловым слоем, а не форматом JSON.

При `apply_on_startup=true` настройки применяются после инициализации
и проверок драйвера в порядке массива. Каждая операция проходит политику,
проверки масок и `verify`. При ошибке дальнейшее применение останавливается,
результат содержит выполненную часть; физические изменения не откатываются
и автоматически не повторяются.

Если настройка покрывает не все обычные записываемые биты, остальные
получаются безопасным физическим чтением, а не из устаревшего кэша.
Драйвер должен поддерживать сериализованное чтение и запись такой настройки.
В отправляемом слове командные биты не активируются, фиксированные биты
получают `fixed_value`. Политика проверяет итоговое отправляемое слово,
а не только сохранённую часть. При отсутствии безопасного механизма
частичное применение не выполняется. Локальная сериализация PS не является
гарантией атомарности относительно независимого внешнего мастера.

Команды, потоки и содержимое блочного носителя в `settings` не помещаются.
Название команды для явного применения v2 этой спецификацией не вводится:
runtime и интерфейсы должны быть реализованы отдельно.

## Телеметрия и события

| Поле `observability` | Тип | Умолчание | Смысл |
|---|---|---|---|
| `telemetry` | `Bool` | `true` | Публиковать доступные сервису наблюдения обмена |
| `events` | `Bool` | `true` | Публиковать попытки операций с побочными эффектами, отказы и результаты |

Телеметрия должна различать перехват внешнего обмена, инициированный PS
опрос и работу с локальным кэшем. Опрос не является пассивным перехватом.
Событие попытки не выдаётся за успешное применение значения устройством.
При ошибке чтения отсутствующее значение не изображается как достоверный
ноль. Публикация не включает опрос, не меняет политику и не разрешает I/O.

Поля управляют публикацией в сервисные журналы, но не гарантируют полный
анализатор шины и не отключают обязательные системные сообщения об ошибках.
Вместимость журналов, предел сохраняемого payload и доступность наблюдений
объявляет реализация. Усечение полезных данных и программные потери
обозначаются явно; неизвестные потери PL не выдаются за посчитанные.

## Проверка и применение

Проверка проходит до изменения активного профиля и до любого I/O:

1. Размер, кодировка, синтаксис JSON, отсутствие повторных ключей.
2. Версия, обязательные поля, типы, перечисления и неизвестные ключи.
3. Наследование, числовые границы, уникальность ресурсов и ссылок.
4. Согласованность масок, эффектов, доступа, кэша, обновления и проверки.
5. Совместимость с зарегистрированными контроллером и обработчиком.
6. Возможность выполнить неявные операции: фоновое чтение, проверку,
   обнаружение повторного подключения и применение настроек.
7. Конфликты адресов, портов, CS и владения ресурсами с другими профилями;
   доступная память и лимиты сборки.

Часть проверок геометрии, наличия и физического состояния возможна только
после обмена. Такой этап выполняется отдельно после успешной статической
проверки; ошибка делает соответствующее устройство недоступным, но не
разрешает более слабые настройки безопасности.

Ошибка содержит путь поля и причину, например:

```text
resources[0].verify.mask: contains self-clearing bits
transport.address: exceeds the MDIO address range
protocol.driver: not supported by this firmware
policy.write.rules[0].resource: unknown resource
```

Это пример формы диагностики, а не новые числовые коды DCP2. Проверка
профиля не должна выполнять пробные записи или вызывать команды устройства.
При неудачной замене работающий профиль сохраняется; нельзя частично
применять политику из ошибочного файла. Если пригодного профиля ещё нет,
устройство остаётся неактивным. Файл с неизвестной версией не разбирается
как старый формат.

|---|---|
| [LAN8720A](examples/device-profile-v2/lan8720.json) | MDIO Clause 22, один обычный регистр, маски, кэш и проверка записи |
| [PCA9536](examples/device-profile-v2/pca9536.json) | I²C, один читаемый регистр входов, битовое поле |
| [Транзакция SPI](examples/device-profile-v2/spi-endpoint.json) | Командный ресурс с непрозрачным двоичным обменом |
| [Поток UART](examples/device-profile-v2/uart-endpoint.json) | Поток RX, ограниченный буфер и переполнение |
| [SD по SPI](examples/device-profile-v2/sd-card.json) | Блочное устройство с определяемой ёмкостью, без форматирования |

LAN8720A и PCA9536 представлены неполными картами: отсутствующие регистры
не доступны по профилю. Маска `0x00FE` регистра LAN8720A `0x1E`
соответствует описанию Interrupt Mask Register в
[Microchip LAN8720A, раздел 4.2.13](https://ww1.microchip.com/downloads/en/DeviceDoc/00002165B.pdf).
Описание PCA9536 и источник его регистрового контракта находятся в
[описании действующих профилей](../../configs/README.md).

Примеры фрагментов для дополнения полного профиля:

```json
{
  "read_effect": {
    "clear_mask": "0x0000",
    "latch_high_mask": "0x0012",
    "latch_low_mask": "0x0004"
  }
}
```

Это пример синтаксиса разных эффектов битов, не разрешение включать
опрос или зеркалирование такого регистра без проверки возможностей моста.

```json
{
  "resource": "irq_mask",
  "match": {
    "value": "0x0000",
    "mask": "0x0000"
  }
}
```

Такое правило в whitelist записи разрешит любые допустимые значения
`irq_mask`; остальные проверки сохраняются. Оно намеренно отсутствует
в полном примере с запрещёнными записями.

```json
{
  "desired": [
    {"resource": "irq_mask", "value": "0x0000", "mask": "0x00FE"}
  ],
  "cache_seed": [],
  "apply_on_startup": false
}
```

Фрагмент настроек не записывает значение в PHY при загрузке. Для явного
применения потребуется разрешение политики и реализация соответствующего
сервисного действия.

Синтаксис файлов можно проверить из корня репозитория:

```sh
for profile_file in docs/reference/examples/device-profile-v2/*.json; do
    jq empty "$profile_file" || exit 1
done
./scripts/check_docs.sh
```

`jq` проверяет только JSON, не все ограничения этой спецификации.
Машиночитаемая JSON Schema пока не поставляется. Реализованный C-загрузчик
строго проверяет подмножество адаптеров мостов; его тесты входят в
`./build.sh check`. Общие проектные примеры этот загрузчик отклоняет.
JSON Schema также не заменит проверку аппаратных возможностей и семантики
конкретного устройства.

## Переход с действующего формата

| Элемент старого файла | Реализованный перенос в v2 |
|---|---|
| `name` | `id`; без автоматического переименования |
| `addr_7b`, `phy_addr` | `transport.address` и указание шины |
| `reg_count` | Явный непрерывный набор сырых ресурсов адаптера моста |
| `max_value_code` | `bvstk_i2c_bridge.options.max_write_value`, не битовая маска |
| `autopoll_regs` и интервалы MDIO | `bvstk_mdio_bridge.options.autopoll_*`, включая порядок |
| `policy`, `whitelist`, `blacklist` | `policy.write.mode`, `rules`, `inactive_rules` |
| `settings` старого профиля | `settings.cache_seed`; не физические записи |
| Свободный кэш | Runtime-состояние; I²C сохраняет прежнюю синхронизацию при `save` |
| `desired` | Остаётся пустым, применение при старте выключено |

Переход на более богатый семантический обработчик — отдельная задача,
требующая проверки карты конкретной микросхемы и реализации всех
выбранных свойств. Нельзя просто переименовать `bvstk_mdio_bridge`
в `mdio_clause22`: это разные контракты поведения.

Возможности сборок перечислены в [таблице поддержки](profiles.md),
действующий MDIO-контракт — в [описании драйвера и сервиса](../development/drivers/mdio.md).
